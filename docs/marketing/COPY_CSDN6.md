# 别再逐个平台手动发文了：我用 Agent 自动跑完 8 个平台，连数据都收回来

先说结论：**这 8 个平台的内容运营，从写稿、分发到回收数据，全程是 Agent 完成的。我没有逐个登录后台，没有手动调格式，也没有一家一家选分类和标签。**

这篇文章本身也是这么发出来的——标题、正文、分类、标签、点发布，都是 Agent 在浏览器里一步步完成的。

## 一、这件事以前有多费时间

维护几个内容号的人都熟悉这个流程：稿子写完后，挨个打开 8 个平台的后台，粘贴正文、调整格式、选分类、填标签、看活动入口，最后点发布。一遍下来几个小时，而且全是重复劳动。

更麻烦的是**数据回收**。发完之后想知道哪篇在涨、哪条标题接不住量，还得再挨个后台点开看一遍。

我后来把这条链路整个交给了 Agent。现在只需要登录一次账号，然后告诉它做什么，比如：

```text
帮我分析一下这 8 个平台的数据，考虑今天的内容怎么发，然后直接做。
```

## 二、用的是什么：一个能把浏览器交给 Agent 的开源项目

没有用复杂的编排平台，也没写爬虫。核心就是一个开源项目 **ai-browser**（MIT，GitHub：`Glittering/ai-browser`）。

它的思路很直接：**把你平时在用的那个浏览器，变成 Agent 可以操作的对象。**

- 登录态是你自己的，窗口是看得见的，Agent 在后台操作时不会抢你的焦点；
- Agent 读到的不是截图，而是带角色、标签和稳定 ID 的语义树，不花视觉 token；
- 遇到扫码、滑块这类验证，你直接动鼠标接管，做完它继续往下跑。

## 三、安装：一条命令

把下面这段话复制给你的 Agent 就行：

```text
帮我安装并配置 ai-browser 这个 MCP server，命令是：
npx -y @glittering0717/ai-browser mcp
装好之后告诉我怎么验证它真的能用。
```

**平台边界（如实说明）**：dmg 安装包目前只有 macOS arm64 版本；上面的 `npx` 方式我在 macOS 和 Linux 上都实测跑通；Windows 还是 experimental 状态，README 里挂着，欢迎来试。

两个名字别搞混：npm 包名带作者 ID `@glittering0717/ai-browser`，GitHub 仓库是 `Glittering/ai-browser`。

遇到问题可以直接让 Agent 排查，或者到 GitHub 提 issue。

## 四、装完先让它干一件真事

项目装好了，先别急着发稿。给它一个最小任务验证链路是否真的通：

```text
用 ai-browser 打开 https://github.com/Glittering/ai-browser，
如果需要登录的话，停下来告诉我。登录状态的话，给项目点个 star。
```

这一步能一次验证三件事：打开页面、读懂结构、点击生效。

**必须说明的是**：如果需要登录，你还是得自己登——扫码和滑块这两步它替不了，也不该让它替。

不想点 star 也完全可以，把网址换成任何一个你需要登录的后台页面，效果一样。

## 五、8 种编辑器，为什么不用写适配代码

这是我最关心的问题：8 个平台用了 8 种不同的编辑器，难道要写 8 套适配？

实际不用。每次遇到新页面，它先调一次 `browse_capabilities` 探测这页提供什么，然后按三级路由选路：

| 级别 | 页面情况 | 做法 |
|---|---|---|
| L1 | 页面自己暴露了数据模型 | 直接读写 JSON，最省 |
| L2 | 语义树里有足够元素 | 按角色和文字定位，按稳定 ID 驱动 |
| L3 | 什么都不给 | 才退化到指针手势，且必须用前后快照对比兜底 |

输入统一走浏览器受信事件通道，所以 Draft.js、ProseMirror、Quill、CKEditor 是同一条路，不需要按框架特判。

8 个平台的实际情况：

| 平台 | 编辑器 / 发布链路 | 结果 |
|---|---|---|
| 掘金 | CodeMirror + 发布弹窗 | 已发 |
| 知乎 | Draft.js（文章 + 回答） | 已发 |
| CSDN | CKEditor + Markdown 导入 | 已发 |
| 头条 | ProseMirror | 已过审 |
| B站 | 跨进程 iframe 编辑器 | 视频 + 专栏均已发 |
| 简书 | contenteditable | 已发 |
| 51CTO | 单选分类弹窗 | 已过审（人工审核） |
| 开源中国 | Tiptap ProseMirror | 已过审（人工复审） |

## 六、数据回收也是同一条链路

发完稿只是上半场。每天早上我让它把各平台的展现、阅读、点赞、收藏抓回来，落进一张表：

```text
把掘金、知乎、CSDN、头条、B站、简书、51CTO、开源中国
这几个后台的文章数据抓一下，整理成一张对比表。
```

选题也跟着变了——哪类标题接得住量，看数据决定，不靠猜。

## 七、小结

跑通「打开页面 → 读懂结构 → 点击生效 → 验证结果」这条链路之后，发稿只是它的第一个任务。同样的逻辑可以放到任何只有 Web 后台、没有 API 的系统上。

几点经验：

1. **扫码和滑块必须留给人**，这是边界也是可信度；
2. **给 Agent 的定位参数要用稳定 ID**，不要用可见文字当选择器，否则页面一改就点空；
3. **每条让读者复制的命令都要自己先跑一遍**，包括包名、参数、平台边界；
4. **命令和边界写清楚比写漂亮重要**，读者照抄出错一次就不会再试。

仓库：https://github.com/Glittering/ai-browser · MIT 协议

跑不通的话，把日志贴到 GitHub Discussions——那是我最想要的输入。
