# 告别 XPath：页面一改版选择器全失效，我用语义树稳定 ID 让 Agent 重新定位

先说结论：**你不必再为每次页面改版重写一遍 XPath。** 把"定位元素"这件事从"匹配一段字符串"换成"读语义树里的稳定 ID"，Agent 就能在当前页面上自己找到那个按钮；点完之后，它还能告诉你这次操作到底有没有真的生效。

这篇文章记录我怎么把一条反复失效的定位链路换掉：三类最常见的失效场景、稳定 ID 到底是什么、ref 失效时如何判断原因，以及一套能直接跑的 MCP 配置和示例。

## 一、XPath 为什么"一改版就全挂"

写过前端自动化的人对这一幕都不陌生：脚本上周还好好的，这周一到 CI 就红。打开报错一看，是某个 XPath 找不到节点了。原因基本跑不出这三类：

1. **DOM 层级变了。** `//div[3]/section[2]/button` 这种按位置数的路径，页面中间插一个容器就整体错位。
2. **可见文案变了。** 依赖按钮文字的去重逻辑，开发把"提交"改成"确认提交"，选择器立刻点空。
3. **动态 class / id 变了。** 前端框架每次构建生成的哈希类名（`btn_x7f2a`）根本没法写进选择器。

这三类失效有个共同点：**脚本把"页面长什么样"写死了。** 页面一变，写死的假设就破。所以我后来换了个思路——不要让脚本去描述页面，让它在运行时读页面当下提供的结构。

## 二、三条定位路线，我为什么选了稳定 ID

网上主流的定位方式大概三条，我把它们和各自的代价摊开对比过：

| 定位方式 | 怎么找到按钮 | 改版后 | 主要代价 |
|---|---|---|---|
| XPath / CSS 选择器 | 匹配路径、class、文字 | 大量失效，要重写 | 前期快，维护成本随改版次数线性上涨 |
| 截图 + 坐标 / 视觉模型 | 看图猜哪个是按钮 | 大部分能自适应 | 慢、贵，且"猜"意味着无法保证点对了；登录态页面尤其容易被验证码打断 |
| **语义树稳定 ID** | 读页面当下渲染出的可访问性树，用 `data-ai-id` 引用 | 重读一次树即可重新定位 | 需要浏览器侧支持语义树导出 |

我选第三条，理由不是它"更先进"，而是它把不确定性收敛了：脚本不再假设页面结构，只持有对**当次读到的节点**的引用。

这里有个反直觉但很重要的细节：**永远不要把可见文字当选择器。** 很多人第一反应是"那我用按钮文字定位不就行了"——但文字是最容易变的东西，页面一改版、甚至只是多语言切换，文字选择器就点空。真正稳的是浏览器给每个可交互节点挂的内部 ID，它和文案无关。

具体到实现，节点引用分两种，各自有明确用途：

- `data-ai-id`（形如 `e:button-12`）：来自语义树，用于 `browse_act` 的点击、输入、上传等操作。
- 老式的 CSS 选择器：只有 `upload` 这类少数操作接受，因为它要定位隐藏的 `<input type=file>`，那种节点语义树里读不到。

## 三、ref 失效时，怎么判断是哪种失效

换成稳定 ID 之后，新的困惑是：引用偶尔也会"找不到目标"。我一开始以为是 bug，后来发现工具其实已经把原因分类返回了——关键是要去看，而不是盲目重试。这套诊断叫 `ref_diagnosis`，三种情况对应完全不同的处理：

| `ref_diagnosis` | 含义 | 正确做法 |
|---|---|---|
| `stale`（过期） | 你在旧树上取的 ref，页面已经被重新读过一次 | 重新读树，拿新 ref，再操作 |
| `never_seen`（从未出现） | 这个 ref 从来没在任何树里出现过 | 多半是把可见文字当成了 ref，或者手滑、用错了标签页——重读也没用 |
| `present_in_tree`（在树里但 DOM 找不到） | 节点在 iframe、shadow root 里，或已经脱离文档 | 换到对应 frame 上下文里操作 |

三种情况工具都返回 `effect_state: "none"`（没有产生任何副作用）和 `retry: "verify_first"`。这意味着**重复点同一个失效引用毫无意义**，但也不会重复提交表单——先把原因读出来再决定动作。这个设计救过我好几次：以前"找不到就重试一遍"的习惯，在支付类按钮上是会出事的。

判断"操作到底有没有生效"，则靠 `browse_diff`：先 `snapshot` 存一份基线，操作后 `diff`，它会返回新增、删除、变化的字段和前后值。这样"我点了"和"页面真的变了"是两件事，后者才是可验证的事实。

## 四、环境与平台边界（如实说）

先把边界讲清楚，省得照着做的人踩空：

- **macOS 安装包（dmg）**：只构建了 `arm64`。它没做公证，首次打开会被 Gatekeeper 拦，需要右键 → 打开。
- **Windows 安装包（`Setup.exe`）**：x64 版本，按用户装到 `%LOCALAPPDATA%\Programs\AI Browser`，不需要管理员权限，装完自动建开始菜单和桌面快捷方式。装、卸、从快捷方式启动我都验过，e2e 套件也在 Win10 上跑过。它没有代码签名，SmartScreen 会拦一次：**更多信息 → 仍要运行**。
- **Linux**：没有安装包，走 `npx`。
- **npx 方式**：macOS 和 Linux 我都实测跑通了，这是 Agent 接入最常用的通道。

## 六、接进 MCP 客户端

把下面这段加进 MCP 客户端配置文件（Claude Desktop 的配置、`~/.cursor/mcp.json`，或项目级 `.mcp.json`）：

```json
{
  "mcpServers": {
    "ai-browser": {
      "command": "npx",
      "args": ["-y", "@glittering0717/ai-browser", "mcp"]
    }
  }
}
```

配好之后，Agent 侧就是一组 `browse_*` 工具。下面三个示例串起来，正好是"读树 → 定位 → 验证"的完整闭环。

## 七、三个可运行示例

**示例 1：读语义树，拿到稳定 ID**

```
browse_navigate  { url: "https://example.com/admin" }
browse_get_tree  {}
```

`get_tree` 返回的是当前页面的可访问性树，每个可交互节点都带一个 `data-ai-id`，比如 `e:button-12`。这个 ID 就是从树里读出来的定位依据，和按钮上写什么字无关。

**示例 2：用稳定 ID 操作，而不是用文字**

```
browse_act  { action: "click", target: "e:button-12" }
```

这里的 `target` 只认语义树里的 ref。如果你把 `target` 写成按钮上的可见文字，会直接得到 `never_seen`——这正是前面说的"别拿文字当选择器"。需要上传文件时才走 CSS 选择器：

```
browse_act  { action: "upload", target: "#import-markdown-file-input", file: "/abs/path/a.md" }
```

**示例 3：操作后做前后快照，确认真的生效**

```
browse_diff  { action: "snapshot" }
browse_act   { action: "click", target: "e:button-12" }
browse_diff  { action: "diff" }
```

`diff` 会告诉你哪些字段新增、删除或变化，以及变化前后的值。"点了按钮"不等于"数据改了"，这一步把两件事分开，是我现在每个关键操作后都会做的动作。

## 八、常见问题

**Q：登录态、扫码、滑块怎么办？全交给 Agent 不行吗？**
A：这部分我坚持留给人。窗口是可见的真人浏览器，扫码和滑块这类涉及身份的动作，人随时接手，接完让流程继续往下跑。这不是偷懒，是边界——把身份动作交给自动化，风险远高于省下的那点时间。

**Q：稳定 ID 会不会过期？**
A：会。它指向"当次读到的节点"，页面刷新或重新读树后要拿新的 ref。看到 `stale` 就重新读树，别在原 ref 上死磕。

**Q：iframe 或 canvas 里的元素怎么办？**
A：iframe 会遇到 `present_in_tree`，需要切到对应 frame 上下文。canvas 则是另一回事——它是语义树的盲区，得走专门的绘制层拦截，那是另一个话题了。

**Q：Windows 能用吗？**
A：能。x64 有 `Setup.exe`，装/卸载和 e2e 套件都在 Win10 上跑过，不是"能编译但不敢担保"的状态。唯一要提前知道的是没做代码签名，SmartScreen 会拦一次（更多信息 → 仍要运行）。CI 只在 macOS 跑单测，所以不是每个版本都在 Windows 复测过——真出问题提 Issue，我按真机复现。

## 九、小结

换掉 XPath 之后，我最大的感受不是"技术升级"，而是**把一次性的写死，换成了运行时的读取**。选择器是在开发时把页面结构写死；稳定 ID 是在运行时读页面当下的结构。页面越常改版，这个差别越值钱。

配合 `ref_diagnosis` 判断失效原因、`browse_diff` 验证操作结果，整条链路从"点了没反应全靠猜"变成"每一步都有据可查"。这套组合尤其适合需要登录态、有多层后台的页面——恰恰是纯 headless 方案最难啃的场景。

项目是 MIT 开源的，仓库在 `github.com/Glittering/ai-browser`，命令行那行 `npx -y @glittering0717/ai-browser mcp` 就是最小接入单元，可以直接复制走。我在找 10 个有"登录态 + 验证码 + 多个后台要操作"这种真实场景的开发者，免费帮你把流程跑通，跑不通也算我一个反面案例。

不想点 star 也完全可以，换成任何需要登录的后台页面，效果一样——能跑通的例子比 star 更有价值。
