## 正文

先说结果：我现在维护 8 个内容平台——掘金、知乎、CSDN、头条、B 站、简书、51CTO、开源中国。从写稿、发布，到第二天回收数据，全程我只说一句话。

以前不是这样的。

不算写稿，光"发"这一个动作，一遍下来是几个小时。打开后台、粘正文、调格式、选分类、填标签，最后点发布。八个平台八套后台，八种编辑器，没有一处是重复的，也没有一处能省。发完之后还想知道哪篇在涨、哪个标题接不住量，就得再挨个后台点开看一遍。时间都花在这种机械的搬运和核对上了。

后来我把这条链路整个交给了一个 Agent。不是写了八个平台的脚本，是给它装了一个能操作浏览器的 MCP server，然后告诉它做什么。

现在的流程是：我登录一次账号，然后说一句"帮我分析一下这 8 个平台的数据，考虑今天的内容怎么发，然后直接做"。剩下的它自己走。

这篇稿子本身也是这么发出来的。标题、正文、配图、分类、点发布，都是它在浏览器里一步步完成的。我只在扫码和滑块的时候出过场——那两步它替不了，也不该让它替。这是边界，也是我对"自动化"这件事的底线：涉及身份的动作必须留给人。

装起来是一条命令，把这句话复制给你的 Agent 就行：

帮我安装并配置 ai-browser 这个 MCP server，命令是：

```bash
npx -y @glittering0717/ai-browser mcp
```

项目叫 ai-browser，MIT 协议，GitHub 上是 Glittering/ai-browser（npm 包名多个作者 ID，别搞混）。

平台边界我说清楚：dmg 安装包目前只有 macOS arm64 版本；上面这条 npx 命令我在 macOS 和 Linux 上都实测跑通；Windows 还是 experimental（实验性），README 里挂着，欢迎来试。遇到任何问题，都可以让你的 Agent 直接解决，或者到 GitHub 给我反馈。

装完先让它干一件真事，别急着发稿。我给的是最小任务：打开项目主页，需要登录就停下来告诉我，登录状态的话给项目点个 star。这一步一次验证三件事——打开页面、读懂结构、点击生效。

不想点 star 也完全可以，把网址换成任何一个你需要登录的后台页面，效果一样。

## 八个平台，为什么不用写八套适配

这是我一开始最担心的问题。八个平台用了八种编辑器：CodeMirror、Draft.js、CKEditor、ProseMirror、Tiptap、跨进程 iframe 的、contenteditable 的。难道要一个个去伺候？

实际不用。它每次遇到新页面，先探测这页提供什么，然后按三级路由选路：页面自己暴露数据模型的，直接读写 JSON；语义树里有足够元素的，按角色和文字定位、按稳定 ID 驱动；什么都不给的，才退化到指针手势，而且必须用前后快照对比兜底。

输入走的是浏览器受信事件通道，所以 Draft.js、ProseMirror、Quill、CKEditor 是同一条路，不按框架特判。

我也在这儿摔过一次：给它的定位参数必须用稳定 ID，不能拿可见文字当选择器。页面一改版，文字选择器就点空，而 ID 不会。这条是我用几次失败换来的，写出来给后面的人少走点弯路。

八个平台的实际结果：掘金、知乎、CSDN、B 站、简书已发；头条、51CTO、开源中国过了人工审核。没有一家是因为"写不动"卡住的。

## 数据也一起收回来

发完稿只是上半场。现在每天早上它把各平台的展现、阅读、点赞、收藏抓回来，落进一张表。哪类标题接得住量，看数据决定，不靠猜。

跑通"打开页面 → 读懂结构 → 点击生效 → 验证结果"这条链路之后，发稿只是它的第一个任务。同样的逻辑可以放到任何只有 Web 后台、没有 API 的系统上。

几条经验收个尾：

1. 扫码和滑块必须留给人，这是边界也是可信度；

2. 定位参数用稳定 ID，不要用可见文字；

3. 每条让读者复制的命令，自己先跑一遍，包括平台边界；

4. 命令和边界写清楚，比写漂亮重要。

仓库在 GitHub，搜 Glittering/ai-browser 就能找到，MIT 协议。

跑不通的话，把日志贴到 GitHub Discussions——那是我最想要的输入。
