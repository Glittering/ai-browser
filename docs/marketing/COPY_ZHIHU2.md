## 主稿（约 1200 字，可直接粘贴）

先说结论：**因为网页编辑器不是给程序用的，是给人手的。** Agent 之前所有的"智能操作"，在编辑器这一层全部失效。

我自己踩过一遍。让 Agent 去知乎发一篇带排版的文章，它能找到标题框、能点发布按钮，但正文粘进去——格式全丢，六个二级标题变成一段纯文本。去 CSDN 发， Markdown 导入器倒是能用，但发布弹窗的标签怎么都选不中。

后来把这类问题拆开看，发现编辑器是自动化里最苛刻的一类目标，原因有三个。

## 一、编辑器维护自己的状态，不吃你那一套

普通 input，你 `element.value = 'x'` 它就显示 x。但 Draft.js、ProseMirror、Quill、CKEditor 这些富文本编辑器，内部维护着一套自己的文档模型和状态机。你用 JS 直接改 DOM，它的模型不知道；模型不知道，渲染就不更新；更麻烦的是粘贴——粘贴在编辑器里不是"插入文本"，是要过一遍编辑器自己的粘贴管线（`DraftPasteProcessor` 这类），决定什么格式保留、什么转换、什么丢掉。

所以正确的做法不是模拟"输入内容"，而是**交给浏览器一个真实的粘贴事件**，让编辑器用自己的规则处理。我最后的解法是合成 `ClipboardEvent` + `DataTransfer(text/html)`，把带格式的 HTML 作为粘贴内容派发进去——六个 h2、四十八个加粗 span，一个不少。

## 二、合成事件和受信事件，是两条路

这里有个更深的坑。用 CDP 派发合成键盘事件（比如 Cmd+V），它是直达渲染器进程的，**不过浏览器进程的加速键路径**——所以普通输入框里能粘贴，到了编辑器里就丢格式。浏览器把"用户真的按了快捷键"和"页面里派发了个假事件"分得很清。

点击和输入要走 `Input.dispatchKeyEvent` / `dispatchMouseEvent` 这种受信输入通道，和真人敲键盘走的是同一条路。好处是所有编辑器通吃，不需要给每个网站写特判代码——我数过，为了发这 8 个平台的稿子，特判代码是零行。

## 三、编辑器会骗你：返回成功，什么都没发生

这是最危险的一类故障。工具返回 success，Agent 信了，继续往下走，错误在第三步之后才暴露，这时候已经放大成一场排查。

我的做法是把"验证"本身做成工具原语：操作前后各取一次页面快照，对比给出显式的 changed/unchanged 判定，附上前后值和 JSON 路径。就这一个设计，拦下了三次"以为填进去了其实没有"——其中一次是粘贴粘进了顶部的搜索框：那个页面里搜索框和正文编辑器都带 `editable` 状态，按 `editable` 过滤就会先抓到搜索框。字数校验拦住了它，没有提交出去。

## 四、所以"让 AI 操作网页"卡在哪

回到问题本身。Agent 操作网页失败，多数不是模型不够聪明，是三层里至少一层没打通：

- **感知层**：给它截图，它就在做图像识别；给它带类型和标签的结构化节点，它才是在"读网页"
- **输入层**：合成事件被现代编辑器大量拒绝，受信事件才通
- **验证层**：没有"操作生效了没有"的原语，错误会被放大而不是被拦住

编辑器只是这三层问题最密集的地方。你看到的是"AI 连一篇文章都发不出去"，底层是这三件事每件都差一点。

> 边界说清楚：以上是桌面浏览器（Electron + CDP）的实践，macOS/Linux 验证过，Windows 没有；手机上厂商限制更严，是另一个问题，不能拿桌面端的结论去套。
