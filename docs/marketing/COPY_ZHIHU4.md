## 正文

省下来了。而且省得最多的环节，和我一开始以为的完全不是同一个。

先说问题里提到的会议纪要和日报——这类我最早也折腾过，结论是"调规则比自己做还累"，后来想明白原因：它们的难点在**理解**，不在**搬运**。Agent 能替人搬运，但替不了人判断"这场会哪些信息值得留"。所以我把它交还给了自己。

真正被我交出去的，是另一类**纯机械**的活。我自己维护 8 个内容平台：掘金、知乎、CSDN、头条、B站、简书、51CTO、开源中国。把"发一篇文章"这件事拆开，机械的部分是这样的：

- 逐个平台打开后台，确认登录态有没有掉；
- 同一个标题和正文，按每个平台的编辑器格式重新贴一遍（CodeMirror、Draft.js、CKEditor、ProseMirror、Tiptap，五种编辑器）；
- 每个平台各填一遍分类、标签、摘要、创作声明；
- 点发布，等审核，再逐个后台核对"到底发出去没有"——这一步最阴险，有的平台点了发布其实躺在草稿箱，链接能打开，但对外不可见；
- 第二天再逐个后台回收数据：阅读、赞、收藏、评论，凑成一张表。

一轮走完，一个下午就没了。而且这里面没有一件事需要动脑子——全是搬运、核对、填表。

## 后来省掉的，正是这一串

现在的形态反过来了。我把选题和标题定好（这部分还是人的活，后面会说为什么），正文写完，然后是一条命令的事：8 个平台的发布全跑完，第二天早上我面前有一张自动回收的数据表，哪个平台在涨、哪篇在掉、哪条标题接不住量，直接看。

不是说这个过程没有代价。说三个我摔过的坑，比说"全自动"有价值：

**第一，发布成功不能信 toast，要信页面状态。** 我发生过不止一次"显示发布成功、其实在草稿箱"的事。有的平台不跳成功页，有的平台发布按钮上面盖着一个反馈弹窗，你的点击全落进弹窗里，发布动作根本没触发。现在我的验收标准是：文章页的状态文字显示"公开/已发布"，而不是弹窗说"成功"。

**第二，定位参数必须用稳定 ID，不能用可见文字。** 平台一次前端改版，"发布文章"四个字还在，按钮的 DOM 结构全变了，按文字找的选择器集体点空。按带稳定 ID 的语义节点定位，改版只需要重新探测一次。

**第三，扫码、滑块、验证码，必须留给人。** 这不是省不掉，是不该省。涉及身份的动作本来就该由人确认。我的设计是 Agent 跑到这一步就停下来说"该你了"，人做完告诉它继续，它接着跑——而不是想方设法替人点掉。

## 但有一笔账没省下来，得说清楚

**写稿本身没有变快。** 选题、角度、标题该不该这么起，这些还是人的活。数据只能告诉你哪类标题接得住量，不能替你想。我自己的分工是：机械环节全部交出去，判断环节全部留给自己。

所以如果问"最后真的省下时间了吗"——答案是每个发布周期从半天变成几分钟，数据回收从半小时变成零。但如果你指望它替你想选题，那省不下，这部分从来就不该归它管。

## 一点出处

这套东西我用的是一个开源项目叫 ai-browser（我自己写的）：一个可见的、常驻登录的 Electron 浏览器，Agent 通过 MCP 工具驱动它读写页面——看到的不是截图，是带角色和稳定 ID 的语义树。MIT 协议，GitHub 搜 Glittering/ai-browser 就能找到。

想验证它是不是噱头，最小的测试任务是：打开项目主页，需要登录就让它停下来你来，登录状态的话顺手点个 star。这一步同时验证打开页面、读懂结构、点击生效三件事。不想点 star 也完全可以，换成任何一个你需要登录的后台页面，效果一样。

说清楚边界：目前 dmg 只有 macOS arm64 版本，npx 方式我在 macOS 和 Linux 上实测跑通，Windows 还是 experimental。这三句必须讲，照抄出错一次就不会有第二次。

你们用 Agent 自动化掉的重复工作里，最意外省下来的是哪个环节？我猜每个人答案都不一样。
