## 正文

## 结论先行

我把 8 个内容平台（掘金、知乎、CSDN、头条、B站、简书、51CTO、开源中国）的发稿链路交给了一个 Agent，用的就是一个 MIT 协议的开源项目 ai-browser。从写稿、分发到回收数据，全程是它跑的；我只在扫码和滑块时出过场。

这篇文章本身也是这么发出来的——标题、正文、分类、点发布，都是 Agent 在浏览器里一步步完成的。

## 为什么需要"可见的浏览器"，而不是无头集群

浏览器自动化的经典痛点是身份：登录态要维持、扫码要掏手机、2FA 要等验证码、滑块要拖。这些环节的共同特征是人类必须在回路里，但又必须能随时接手。

无头集群的思路是起一个干净的临时实例跑完即弃，代价是登录态不共享，脚本每天的第一项工作是重新登录。复制用户 profile 能带上登录态，但两个实例并发占用同一 profile 会撞锁，浏览器一升级 profile 结构跟着变。

ai-browser 的形态是**常驻、可见、持久登录的 Electron 窗口**，同时暴露两套等价接口：

- **MCP stdio**：20 个 `browse_*` 工具，任何 MCP 客户端即插即用；
- **WebSocket JSON-RPC**：`ws://localhost:9223` 上的 `ui.*` 方法，给需要精细控制的场景。

两套接口走同一套页面管理内核。Agent 在后台操作时不抢焦点，窗口是看得见的，随时可以动鼠标接管。

## 感知：语义树，不是截图

Agent 拿到的页面表示是带 role/label/稳定 ID 的语义可访问性树，附带 context：哪个弹窗开着、哪个字段必填、刚才弹出的成功消息是什么、当前是不是登录态。

这直接决定了 8 种编辑器要不要写适配。八个平台的编辑器分别是 CodeMirror、Draft.js、CKEditor、ProseMirror、Tiptap、跨进程 iframe 的、contenteditable 的。实际一套适配都没写——输入统一走浏览器受信事件通道，同一条路覆盖全部。

定位参数必须用**稳定 ID**，不要拿可见文字当选择器。页面一改版，文字选择器就点空，ID 不会。这是我自己摔过几次换来的。

## 安装与平台边界

一条命令，把它交给你的 Agent 就行：

```text
帮我安装并配置 ai-browser 这个 MCP server，命令是：
npx -y @glittering0717/ai-browser mcp
```

平台边界如实说明：dmg 安装包目前只有 macOS arm64 版本；`npx` 方式在 macOS 和 Linux 上都实测跑通；Windows 还是 experimental 状态，README 里挂着，欢迎来试。国产 Linux 发行版只要 Node 版本满足要求即可，无额外系统依赖。

npm 包名带作者 ID `@glittering0717/ai-browser`，GitHub 仓库是 `Glittering/ai-browser`，两个名字别搞混。

装完先给一个最小任务验证链路：打开项目主页，需要登录就停下来告诉你，登录状态的话给项目点个 star。这一步一次验证打开页面、读懂结构、点击生效三件事。不想点 star 也完全可以，换成任何一个你需要登录的后台页面，效果一样。

## 8 个平台的实际结果

| 平台 | 编辑器 / 发布链路 | 结果 |
|---|---|---|
| 掘金 | CodeMirror + 发布弹窗 | 已发 |
| 知乎 | Draft.js（文章 + 回答） | 已发 |
| CSDN | CKEditor + Markdown 导入 | 已发 |
| 头条 | ProseMirror | 已过审 |
| B站 | 跨进程 iframe 编辑器 | 视频 + 专栏均已发 |
| 简书 | contenteditable | 已发 |
| 51CTO | 单选分类弹窗 | 已过审（人工审核） |
| 开源中国 | Tiptap ProseMirror | 已过审（人工复审） |

没有一家是因为"写不动适配"卡住的。卡住的全是身份环节——而那一部分本来就该由人来做。**扫码和滑块必须留给人**，这是边界也是可信度。

## 数据回收

发完稿只是上半场。每天早上让它把各平台的展现、阅读、点赞、收藏抓回来落进一张表，哪类标题接得住量看数据决定，不靠猜。

跑通「打开页面 → 读懂结构 → 点击生效 → 验证结果」这条链路之后，发稿只是第一个任务。同样的逻辑可以放到任何只有 Web 后台、没有 API 的系统上。
