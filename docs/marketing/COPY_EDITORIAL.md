## 1. InfoQ 投稿（约 1800 字）

**标题：**`Agent 浏览器的三条技术路线：像素、DOM 快照与语义层，各自的成本边界在哪`

**正文：**

```
## 引言

Coding Agent 在 2026 年已经相当可用，但"让 AI 替我操作网页"这件事始终差一口气。
问题不在模型能力，而在于我们给 Agent 的**输入抽象层**选错了。

## 三条路线

### 路线一：像素

流程是：截图 → 视觉模型读图 → 输出坐标 → 点击。

代价有三层：
1. 成本：每步一张图进上下文。10 步任务 = 10 张图，视觉 token 是纯文本的几十倍。
2. 稳定性：坐标绑定在像素上。滚动 100px、弹一个 toast、响应式布局切一档，坐标全废。
3. 时效性：toast 提示"发布成功"一秒消失，截图根本来不及。

最致命的是 canvas：canvas 上没有任何 DOM 节点，像素路线只能靠 OCR 猜。

### 路线二：DOM 快照

Playwright、chrome-devtools-mcp 是这一路。比像素稳得多，但有两个没解决的前提：
- **身份**：给你的 Agent 是临时实例，登录态、扫码记录、2FA 都不在里面。每次重登，而这是自动化里最贵的一段。
- **盲区**：canvas 应用在 accessibility tree 里是空的。

### 路线三：语义层

把页面转成带类型/标签/值/状态/可执行动作的结构，每个节点配稳定 ID；再把弹窗、必填提示、成功消息、登录态一起作为 context 返回。
Agent 拿到的不是图，是可寻址、可验证的结构。

## 三个被低估的工程细节

**1）输入通道决定适配成本**
要走 CDP 的 `Input.dispatchKeyEvent` / `dispatchMouseEvent`，不是合成 JS 事件。
差别是真实的：Draft.js、ProseMirror、Quill、CKEditor 都吃这一条通道，**不需要任何网站特判**。点击后再用 `elementFromPoint` 校验命中。

**2）canvas 其实不需要 OCR**
2D canvas 的文字是在 `ctx.fillText()` 里画出来的——在绘制调用层把字符串截下来即可：

{
  "text": "AI Browser wrote this - no screenshot, no OCR",
  "font": "20px Excalifont, Xiaolai, sans-serif",
  "at": { "x": 10, "y": 13.2, "width": 937.4, "height": 42.2 }
}

字体、坐标、颜色都在，零 OCR。只有 WebGL 才需要截图，且默认关闭。

**3）"验证"必须是原语，不是自查**
最高频的故障不是报错，是**工具返回 success 但世界没变**。Agent 信了，继续走，第三步之后错误已经被放大到看不出原样。
所以让每个动作显式返回 changed/unchanged + 前后值 + 路径，并对页面数据模型做指纹。这样"只改 canvas 数据、DOM 零变动"的操作也能识别。

## 选型建议

按三个问题分：
1. 是否需要真实登录态？需要 → 排除临时实例方案，或接受"人接管"形态。
2. 是否涉及 canvas？涉及 → 排除纯 DOM 方案。
3. 是否需要可验证的执行结果？需要 → 确认方案是否把 diff 做成原语。

## 边界

macOS / Linux 已测，Windows 未测；首次启动约 110MB 引擎数据；控制端口只绑 localhost 且无鉴权。
```

## 2. 少数派（个人工作流 · 约 1800 字 · 原创首发 · 必配图）

**标题：**《我用 AI 副驾浏览器整理周报的一天：哪些地方比脚本好用，哪些不如》

**正文骨架（写成完整文章）：**

```
开头：一件每周都要做的破事。整理周报要从五个后台把数据抄下来，写脚本维护不动，不写脚本每周半小时。

一、为什么脚本救不了我
- 登录：公司 SSO + 短信验证码
- 结构：后台改版一次，选择器全废
- 富文本：有些内容要发到带编辑器的后台
- 结论：维护脚本的成本超过了手动操作的成本

二、换了个思路：让 Agent 用我的浏览器
- 窗口常驻可见，登录一次长期有效
- 遇到验证码我自己扫，它等着（截图/无头方案在这里直接死）
- 读的是语义树不是截图，所以后台改版不怕

三、真实一天的记录（配截图）
- 09:10 打开三个后台，取数
- 09:25 让它把数据整理成表格
- 09:40 发到带 Draft.js 编辑器的后台（这里踩了个坑：程序化粘贴格式全丢，最后是合成 ClipboardEvent 解决的）
- 09:55 复核：用 diff 确认发布真的生效了

四、什么情况下它不如脚本
- 明确：高频、稳定、无需登录的批量任务，脚本更快更便宜
- 语义树适合"低频、多变、需要登录"的场景
- 它不无头，所以不适合服务器批量跑

五、小结：这不是"更强"的自动化，是补齐了"需要身份"的那一段。

（文末一行：项目 MIT 开源，仓库链接；想试：npx -y @glittering0717/ai-browser mcp）
```
