## 正文

有，而且"按任务分配模型"这个设计正在从技巧变成标配。我自己写的一个工具里就有一版，这里拆开讲它怎么工作、以及真正难的地方在哪。

先说什么样的任务需要分配。实际用下来， Agent 接到的任务至少分三种，用一种模型、一种策略全扛，是低效的：

**第一种是一次性就能定的小任务。**"这个输入框填什么""这个页面现在是什么状态"。特点是不需要规划，一轮工具调用就有答案。给它最强的模型是浪费—— latency 和成本双输，而正确率并没有提升。

**第二种是需要拆解的多步任务。**"把这篇文章发到 8 个平台"。这种任务的价值全在规划：先后顺序、每步的依赖、哪一步失败了要重来还是跳过。规划模型和执行模型分开，是这类任务的标准结构。

**第三种最特殊：必须操作真实网页的任务。**它不需要多聪明，需要的是另一套东西——稳定的元素定位、跨 iframe 的写入、还有最容易被忽略的：**确认操作真的生效了**。

## 三级路由：按任务性质选路，不按模型强弱选路

我在 ai-browser 里实现的路由是按这个逻辑分的，核心思想是"任务性质决定用哪层能力"：

- **L1，直接执行层。** 页面自己暴露数据模型的（有 API、有 JSON 状态），直接读写数据，不绕任何界面。最快也最可靠，因为不经过渲染层。
- **L2，语义操作层。** 页面只给界面不给数据的，读带角色、标签、稳定 ID 的语义树，按节点定位、按受信事件通道操作。这一层覆盖绝大多数 Web 后台。
- **L3，手势兜底层。** 前两层都不给的（纯 canvas、什么都不暴露的），才退化到指针手势，而且必须带前后快照对比兜底——点了之后页面到底变没变，要用数据说话，不能信"我点了"。

注意这个分法不是按模型分的，是按**页面给你什么**分的。同一个任务里，三个平台可能走三条不同的路，用的是同一个模型。分配模型当然有价值，但先把"任务性质 → 能力层级"这件事想清楚，比盲目上多模型收益大。

顺带说一句边界设计：路由不管分几级，涉及身份的动作——扫码、滑块、验证码——都必须停在 Agent 外面。L1/L2/L3 分的是能力层级，不是信任层级，这一层不归路由管。

## 真正的难点：验证，不是分配

这部分是我觉得最值得说的。多模型路由的教程很多，但有个更基础的问题被普遍跳过：**工具返回 success，不等于事情办成了。**

我踩过的坑：点击回执说成功，页面其实被一个弹窗盖住，点击落进了弹窗按钮；粘贴回执说写入 2000 字，编辑器里其实只有前 100 字；发布弹窗显示"发布成功"，文章躺在草稿箱。每一个都是"返回成功、实际失败"。

所以我在路由旁边加了一个验证原语：操作前后各取一次页面快照，给出显式的"变了/没变"判定加数据指纹。canvas 里画了字但 DOM 一个字节没动的，也能抓到。这个原语加上之后，"分配模型"才有意义——否则你只是在把失败从一个模型转嫁给另一个模型。

## 一点冷静的

也不是所有场景都值得上多模型路由。任务单一、工具面干净的场景，单模型加一套好工具往往更稳——路由本身引入的复杂度和失败模式，是实打实的成本。我的判断标准很俗：只有当"不同任务的性质差异"开始明显影响成功率时，再上分级，不要提前优化。

## 出处

上面这套三级路由是我在开源项目 ai-browser 里实现的其中一层（MIT，GitHub 搜 Glittering/ai-browser）：一个 Agent 驱动的可见浏览器，17 个 browse_* MCP 工具，语义树输入 + 受信操作 + diff 验证。想试的话，最小验证任务是打开项目主页，需要登录就停下来自己登，登录状态的话顺手点个 star——一次验证打开页面、读懂结构、点击生效。不想点 star 也完全可以，换成任何需要登录的后台页面，效果一样。

边界照旧：dmg 只有 macOS arm64，npx 方式 macOS 和 Linux 实测跑通，Windows 还是 experimental。

你们在实际项目里做任务分级了吗？是按模型能力分的，还是按任务性质分的？想听听不同走法的效果。
