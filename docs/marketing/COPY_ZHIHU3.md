## 标题

`维护 8 个内容平台的人，后来都把发稿交给了 Agent：聊聊这件事是怎么成立的`

## 正文要点成稿（约 1700 字）

先说一个可能有点反直觉的判断：**"把发稿交给 Agent"这件事，过去做不到，不是因为 Agent 不够聪明，而是因为它拿不到页面。**

我们给它的输入通常是一张截图。截图的问题不在于看不清，而在于它把网页的**结构**压成了像素——哪个是标题、哪个是按钮、哪个输入框有名字、现在是什么状态，这些信息在截图里全丢了。Agent 只能靠猜坐标去点，页面一滚、一改版，就集体失明。

所以真实的工作流长期是这个样子：人写稿，人搬运，人调格式，人选分类标签，人点发布，人事后挨个后台回收数据。Agent 能帮上的，多半只是"帮我润色一段文字"。

## 转折点在于换一种输入

后来我换了个思路：不让 Agent 看页面，让它**读页面**。

具体说，是给它一个带 role、label、稳定 ID 的语义可访问性树。每个元素不再是一块像素，而是一个有身份、有状态、有可执行动作的节点：

```json
{
  "role": "textbox",
  "label": "请输入文章标题（5～100 个字）",
  "states": ["visible", "focused"],
  "actions": ["type", "clear", "focus"]
}
```

再顺手把 context 一起塞进去：哪个弹窗开着、哪个字段必填、刚才弹出的成功消息是什么、当前是不是登录态。这样它至少不该再问"我是不是已经登录了"。

这一步看起来只是换了个输入格式，但它把问题从"视觉识别"变成了"结构化操作"——后者是 Agent 本来就擅长的。

## 八个平台，八种编辑器，为什么不用写八套适配

这是我一开始最担心的问题，也是我觉得最值得说清楚的一点。

八个平台用了八种编辑器：CodeMirror、Draft.js、CKEditor、ProseMirror、Tiptap，还有跨进程 iframe 的和 contenteditable 的。按常规思路，这是八套适配。

实际一套都没写。原因有两层：

第一层是**输入**。所有编辑器的写入都走浏览器受信事件通道，Draft.js、ProseMirror、Quill、CKEditor 是同一条路，不需要按框架特判。富文本编辑器之间的差异，主要在"怎么把内容送进去"这一层，而这一层被统一了。

第二层是**定位**。遇到新页面先探测这页提供什么，然后按三级路由选路：页面自己暴露数据模型的，直接读写 JSON；语义树里有足够元素的，按角色和文字定位、按稳定 ID 驱动；什么都不给的，才退化到指针手势，而且必须用前后快照对比兜底。

这里有个我摔过几次才记住的教训：**定位参数一定要用稳定 ID，不能拿可见文字当选择器。** 平台一次前端改版，文字选择器全部点空，ID 不会。这一条不值钱，但能省掉很多"昨天还能跑今天点什么都没反应"的时间。

## 但有一条线我不建议你交出去

写了这么多"能自动"，得把边界说清楚，否则这篇就变成吹了。

**扫码和滑块必须留给人。** 这不是能力问题，是设计问题——涉及身份的动作，本来就该由人确认。我把人工介入点设计成"Agent 停下等人，人做完它继续"，而不是抢占焦点替人点掉。前者是工具，后者是风险。

同理，安装时我把话说在前面：dmg 安装包目前只有 macOS arm64 版本；`npx` 方式我在 macOS 和 Linux 上都实测跑通；Windows 还是 experimental 状态。这三句必须写，读者照抄出错一次就不会再试第二次。

装完也别急着发稿。我给的最小验证任务是：打开项目主页，需要登录就停下来告诉我，登录状态的话给项目点个 star。这一步一次验证三件事——打开页面、读懂结构、点击生效。不想点 star 也完全可以，换成任何一个你需要登录的后台页面，效果一样。

## 实际结果与一点保留

八个平台的实际情况：掘金、知乎、CSDN、B站、简书已发；头条、51CTO、开源中国过了人工审核。这篇文章本身也是这条链路发出来的。

我也说点保留。它并没有让"写稿"变快——选题、角度、标题该不该这么起，这些仍然是人的活，数据只能告诉你哪类标题接得住量，不能替你想。它替掉的是搬运、格式、分类标签、回收核对这类机械环节。这个边界划清楚，预期才不会错位。

跑通「打开页面 → 读懂结构 → 点击生效 → 验证结果」这条链路之后，发稿只是它的第一个任务。同样的逻辑可以放到任何只有 Web 后台、没有 API 的系统上。
