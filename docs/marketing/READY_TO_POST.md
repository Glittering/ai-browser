**正文（约 1800 字，可直接贴）**

```
做 Agent 工具时反复碰到同一个问题：让 AI 去知乎/CSDN/后台发一篇带排版的文章，它要么卡在登录，要么读不懂弹窗，要么富文本编辑器里打不出字。

我把同一个任务在三条路线上各跑了一遍，记录真实数据。

## 一、三条路线

**路线 1：截图 + 视觉模型**
流程：截图 → 视觉模型读图 → 输出坐标 → 点击。
问题不在准确率，在抽象层：
- 每次交互一张图进上下文。10 步任务 = 10 张图，视觉 token 是纯文本的几十倍。
- 坐标绑的是像素。滚动 100px、弹个 toast、响应式切一档，坐标全废。
- toast 提示"发布成功"一秒消失，截图根本来不及。

**路线 2：Playwright / chrome-devtools-mcp**
比截图稳得多，但有个硬前提：**它给你的 Agent 一个临时浏览器实例**。
我的登录态、扫码记录、2FA 不在这个实例里。每次都要重新登录——而这恰好是自动化里最贵的一段。
另一个问题：canvas 应用在 DOM 层是空的，accessibility tree 什么都读不到。

**路线 3：语义树（AI Browser 的做法）**
窗口是你桌面上那个常驻的 Electron 浏览器，登录态持久。Agent 通过 MCP 或 WebSocket 驱动它，读到的不是像素：

```json
{
  "role": "textbox",
  "label": "请输入文章标题（5～100 个字）",
  "value": "AI Browser 测试标题",
  "states": ["visible", "focused"],
  "actions": ["type", "clear", "focus"]
}
```

外加 context：当前弹窗、必填提示、成功消息、登录态。

## 二、关键实现点

**1）输入必须走 CDP 受信事件**
`Input.dispatchKeyEvent` / `dispatchMouseEvent`，不是合成 JS 事件。
差别是真实的：Draft.js、ProseMirror、Quill、CKEditor 都吃这一条通道，**不需要任何网站特判**。
点击后还要用 `elementFromPoint` 校验确实命中，避免"点到隔壁元素"。

**2）canvas 不需要 OCR**
2D canvas 的文字是在 `ctx.fillText()` 里画出来的——那就在绘制调用层把字符串截下来：

```json
{
  "text": "AI Browser wrote this - no screenshot, no OCR",
  "font": "20px Excalifont, Xiaolai, sans-serif",
  "at": { "x": 10, "y": 13.2, "width": 937.4, "height": 42.2 }
}
```

字体、坐标、颜色全在，零 OCR。只有 WebGL 才保留截图路径，且默认关闭。

**3）"操作生效了没有"应该是工具原语，不是事后自查**
我踩得最狠的坑：工具返回 success，但页面上什么都没发生。Agent 信了，继续走，错误在第三步之后才暴露。
所以做了 `browse_diff`：快照前后对比，返回显式 changed/unchanged 判定 + 前后值 + JSON path，并对页面数据模型做指纹。
ComfyUI 这类只改 canvas 数据、DOM 零变动的操作，也能被识别。

## 三、结果

单任务（登录已就绪的前提下）：

| | 截图流 | Playwright MCP | 语义树 |
|---|---|---|---|
| 进入登录态 | 需重新登录 | 需重新登录 | 复用常驻会话 |
| 富文本编辑器 | 光标进不去 | 视站点而定 | CDP 通道，无特判 |
| canvas 内容 | OCR 猜 | 读不到 | 直接取字符串 |
| 上下文成本 | 高（视觉 token） | 中 | 低（纯文本） |

## 四、踩坑清单

1. Cmd+V 走 CDP 直达渲染器，不过浏览器进程加速键，合成键不触发原生粘贴 → 用 ClipboardEvent + DataTransfer(text/html) 派发 paste。
2. `browse_evaluate` 不等 Promise，含 `await` 的 IIFE 返回 `{}` → 拆成"触发 → 等待 → 取结果"两段。
3. 标签类控件是自定义组件，合成 `click()` 不吃 → 用 `press ArrowDown` + `Enter` 受信选中。
4. 发布结果别信 toast，以 URL 跳转 + 文章页 200 + 正文可读为准。

仓库：https://github.com/Glittering/ai-browser · MIT · macOS/Linux 已测，Windows 未测。
```

先说结论：不是模型不够聪明，是它既"看不见"也"碰不到"。

Coding Agent 之所以强，是因为它操作的对象是文本——代码文件有确定的结构、确定的地址、确定的可验证结果（编译、测试、diff）。

而手机 Agent 面对的是：为人类眼睛设计的渲染结果。

## 三堵墙

**第一堵：感知被降级成了图像识别**

主流做法是截图 → 视觉模型读图 → 猜坐标 → 点。

这个转换丢掉了三样东西：
- 结构：页面本来是树，截完图变成像素矩阵
- 稳定性：坐标绑在像素上，滚一屏、弹个 toast、响应式切一档，坐标全废
- 时效性：toast 一秒消失，截图根本来不及

更麻烦的是 canvas。canvas 上没有任何 DOM 节点，基于 accessibility tree 的方案在这里拿到的是**空的**。而 canvas 文字其实是在 `ctx.fillText()` 里画出来的——那就在绘制调用层把字符串直接截下来：

{
  "text": "AI Browser wrote this - no screenshot, no OCR",
  "font": "20px Excalifont, Xiaolai, sans-serif",
  "at": { "x": 10, "y": 13.2, "width": 937.4, "height": 42.2 }
}

字体、坐标、颜色都在，零 OCR。

**第二堵：身份与信任边界**

临时浏览器实例解决不了登录态——你的扫码记录、2FA、公司 SSO 都不在那个实例里。

但你又不可能真的把账号全权交给 Agent：滑块、验证码、支付确认，这些人类必须留在回路里。

所以正确的形态不是"全自动"，而是"人随时能接管"：窗口常驻可见，Agent 在后台干活，遇到人机验证时人直接动鼠标，Agent 在对话里等着就行。没有交接 API，也没有权限弹窗。

## 第三堵：没人负责验证

这是我踩得最狠的一个坑。

工具返回 success，但页面上什么都没发生。Agent 信了，继续往下走，等到第三步才暴露——这时候错误已经被放大了。

所以"操作到底生效了没有"必须是工具原语：快照前后对比，返回显式的 changed/unchanged 判定 + 前后值 + 路径，再对页面数据模型做指纹。这样连"只改 canvas 数据、DOM 零变动"的操作也能被识别。

## 为什么手机更难

桌面端至少有 CDP 和相对稳定的 accessibility tree。手机端没有：厂商限制、App 内部状态不可见、系统级自动化接口受限。

我的做法是桌面端方案（Electron + MCP + WebSocket），不是手机端方案——这个边界得说清楚，不能拿桌面端的成果去蹭手机 Agent 的热度。

## 边界

macOS / Linux 已测，Windows 没测；首次启动要拉 ~110MB Electron 引擎；控制端口只绑 127.0.0.1 且没有鉴权，别转发这个端口。
```

一、路线一：像素。截图 → 视觉模型 → 输出坐标 → 点。
   成本：每步一张图。精度：绑在像素上。失效模式：toast 一闪而过。
   本质问题：把"读网页"变成了"图像识别"。

二、路线二：DOM 快照 / Playwright。
   稳得多，但给你的是临时实例——登录态不共享。
   而且 canvas 里根本没有 DOM，accessibility tree 是空的。

三、路线三：语义树。
   把页面转成带类型/标签/状态/可执行动作的结构，配稳定 ID。
   纯文本进上下文，页面位移不影响。
   canvas 内容从 fillText 绘制调用里直接取字符串，不需要 OCR。

四、真正的分水岭不是"能不能操作"，是"能不能确认操作生效了"。
   工具返回 success 但页面没变，是最高频也最贵的一类故障。
   所以验证必须是原语：显式 changed/unchanged + 前后值 + 路径。

五、边界（如实说）：macOS/Linux 已测，Windows 没测；首次启动 ~110MB；控制端口只绑 localhost 且无鉴权。
```

**禁忌**：禁用"宝藏/封神/豁然开朗/彻底解放"；外链只放文末（放开头会被压推荐）；**同一题材在知乎只发一次**（我们已经发过 3 次，这是教训）。
