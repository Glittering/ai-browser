## 标题

`把 8 个平台的发稿流程交给 Agent：一次浏览器自动化的落地实践`

## 正文要点成稿（约 1600 字）

### 一、问题：机械搬运吃掉了大部分时间

维护 8 个内容平台（掘金、知乎、CSDN、头条、B站、简书、51CTO、开源中国），写稿不是最耗时的环节，"发"才是。一遍流程走完要几个小时：

1. 逐个打开平台后台；
2. 粘贴正文，按各站规则调格式；
3. 选分类、填标签、看活动入口；
4. 点发布，等审核状态变化；
5. 事后逐个后台回收展现、阅读、点赞数据。

八套后台、八种编辑器，没有一处能省。这部分工作技术含量低，但占用的整块时间无法压缩。

### 二、方案：把浏览器交给 Agent，而不是写八个平台的脚本

没有选"给每个平台写一个发布脚本"的路线。八个平台三种前端框架、两种编辑器形态，脚本的维护成本会随平台改版线性上升，而改版是常态。

改用 ai-browser（MIT，Electron + MCP）：一个常驻、可见、持久登录的浏览器窗口，通过 MCP 暴露 20 个 `browse_*` 工具给 Agent。

关键设计是感知方式。Agent 拿到的不是截图，是带 role/label/稳定 ID 的语义可访问性树，同时附带 context：哪个弹窗开着、哪个字段必填、刚才弹出的成功消息、当前是否登录态。

这一条直接决定了适配工作量。输入统一走浏览器受信事件通道，CodeMirror、Draft.js、CKEditor、ProseMirror、Tiptap 是同一条路，不需要按框架特判。实际落地时一套编辑器适配代码都没写。

### 三、实施：三级路由与踩过的坑

遇到新页面时按三级路由选路：

| 级别 | 页面情况 | 做法 |
|---|---|---|
| L1 | 页面自己暴露了数据模型 | 直接读写 JSON，最省 |
| L2 | 语义树里有足够元素 | 按角色和文字定位，按稳定 ID 驱动 |
| L3 | 什么都不给 | 才退化到指针手势，且必须用前后快照对比兜底 |

实施中确认有效的几条：

1. **定位参数必须用稳定 ID，不能用可见文字当选择器。** 平台一次前端改版，文字选择器全部点空，ID 不会。这是用几次失败换来的，也是最值得提前说清楚的一条。
2. **涉及身份的动作必须留给人。** 扫码和滑块这两步 Agent 替不了，也不该让它替。人工介入点设计成"Agent 停下等人，人做完它继续"，不是抢占焦点。
3. **每条给读者的命令自己先跑一遍。** 包括包名、参数、平台边界。读者照抄出错一次就不会再试第二次。

### 四、安装命令与平台边界

```text
帮我安装并配置 ai-browser 这个 MCP server，命令是：
npx -y @glittering0717/ai-browser mcp
```

平台边界如实说明：dmg 安装包目前只有 macOS arm64 版本；`npx` 方式在 macOS 和 Linux 上都实测跑通；Windows 还是 experimental 状态，README 里挂着。

装完先做最小验证再上生产流程：让 Agent 打开项目主页，需要登录就停下来告知，登录状态的话给项目点个 star。这一步同时验证打开页面、读懂结构、点击生效三件事。不想点 star 也完全可以，换成任何一个需要登录的后台页面，效果一样。

### 六、数据回收

发完稿只是上半场。每天让 Agent 把 8 个平台的展现、阅读、点赞、收藏抓回来落进一张表，哪类标题接得住量看数据决定，不靠猜。写稿之外的机械环节（搬运、格式、分类标签、回收核对）已全部移交。

### 七、小结

跑通「打开页面 → 读懂结构 → 点击生效 → 验证结果」这条链路之后，发稿只是它的第一个任务。同样的逻辑可以放到任何只有 Web 后台、没有 API 的系统上，包括内部运维平台。

对运维场景的价值在于：不必等平台方排期开 API，也不必为每个系统写一套自动化脚本。
