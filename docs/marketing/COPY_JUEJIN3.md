## 一、其实非常简单，我就用了一个项目

不是什么复杂的编排平台，也没写一堆爬虫脚本。就一个东西：**ai-browser**。

它做的事很朴素——**把你平时用的那个浏览器，直接变成 agent 可以操作的对象**。登录态是你的，窗口是看得见的，遇到扫码和滑块你能随时接手，接完它继续往下跑。

仓库在这里：https://github.com/Glittering/ai-browser

## 二、先说边界，再给安装命令

讲怎么装之前先把话说清楚，免得你白跑一趟：

- **桌面 App 的安装包目前只发了 macOS arm64**（一个 dmg，未签名，首次要右键→打开）；
- **但下面这条 MCP 命令不是走安装包**——它会按你的系统现拉一份 Electron，**macOS 和 Linux 都实测过**；Windows 在 README 里标的是 experimental：纯 Electron + CDP，应该能跑，但没人验过，`npm install` 和窗口层要你自己趟（跑通的话麻烦回来说一声）；
- Node ≥ 18；
- 首次启动会拉一个约 110MB 的引擎，**一次性**，之后复用。

满足的话，最省事的装法是把这段直接复制给你的 agent（Claude Code / Cursor / 任何支持 MCP 的客户端都行）：

```
帮我安装并配置 ai-browser 这个 MCP server，命令是：
npx -y @glittering0717/ai-browser mcp
装好之后告诉我怎么验证它真的能用。
```

**注意包名**：npm 上是 `@glittering0717/ai-browser`（scope 是作者 ID），GitHub 仓库是 `Glittering/ai-browser`，两个不一样，别装错。

手动配置就加进 MCP 配置里：

```json
{
  "mcpServers": {
    "ai-browser": {
      "command": "npx",
      "args": ["-y", "@glittering0717/ai-browser", "mcp"]
    }
  }
}
```

国内可以挂镜像加速首次下载：

```bash
ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/ npx -y @glittering0717/ai-browser mcp
```

至于「把已登录的浏览器交给它」这件事：密码字段在语义树里**不返回 value，只返回 `value_sensitive: true`**——因为整棵树是要喂进 agent 上下文的，不应该带秘密。代码 MIT 开源，工具面一共 17 个，README 里全部列出来了。

## 三、先让它干一件真实的事：点个 star

装完别跑 hello world。判断「agent 到底能不能操作网页」，不要用静态 demo 页——那种页面上点的不是真实按钮，是作者给你摆好的姿势。挑一个有约束的目标：**要登录、按钮状态会变、结果肉眼可见**。

我用的就是这篇自己的仓库：

> 用 ai-browser 打开 https://github.com/Glittering/ai-browser，
> 在语义树里找到 role 是 button、label 是 Star 的那条节点，拿到它的 `data-ai-id`（形如 `e:button-12`），
> 用 `browse_act` 点它，再用 `browse_diff` 看 verdict 是不是 `changed`。
> 注意：没登录 GitHub 的话这步会失败——这是设计的一部分，不是 bug。

它一次回答三个问题，也正好是所有 GUI 自动化的三个死角：

1. **浏览器真的接管了你的登录态**——没登录就点不动，会如实失败，不会假成功；
2. **它不是在盲点坐标**——语义树能按 role + label 从一整页按钮里把目标挑出来；
3. **它不是"我以为点了"**——diff 会显式给出 changed / unchanged。

这里有个容易踩的点：**`target` 收的是 `data-ai-id`，不是按钮上的可见文字**。直接把 "Star" 填进 target 会点空，顺序必须是「先读树拿 id → 再用 id 行动」。

换成你自己的目标，模板只有一句：

> 打开 <你的页面>，在语义树里找到 <某个点了之后状态会变的按钮>，拿到它的 data-ai-id，点它，用 diff 确认状态变了。

不想给我点 star 也完全可以——把网址换成任何一个需要登录的页面、任何一个会改变状态的按钮，效果一模一样。这步的价值是那个"变化"，不是那颗星。

## 四、它凭什么跨 8 种编辑器不用适配

每次遇到一个新页面，它不猜。一次 `browse_capabilities` 会先报告这页提供什么，然后选路：

- **L1**：页面自己暴露了数据模型 → 直接读写 JSON，最省；
- **L2**：语义树里有足够元素 → 用 role/label 定位，按稳定 ID 驱动；
- **L3**：什么都不给 → 才退化到指针手势，并且必须用 diff 兜底。

掘金（CodeMirror）是 L2，知乎（Draft.js）是 L2，B站那个跨进程 iframe 是 L2 加一次 target attach。八个平台落在同一套路由里——所以没有任何一家的代码是为它单独写的。

输入走 CDP 受信事件，Draft.js / ProseMirror / Quill / CKEditor 走的是同一条通道。

## 六、三个真实的坑

**坑 1：paste 的回执不可信。**
掘金（CodeMirror）返回 `landed_chars: 0`，但内容其实已经写进去了。必须独立调 `getValue()` 数一遍——只信回执就会再粘一次，正文变成两份。

**坑 2：语义树里有两个 editable，第一个是搜索框。**
知乎页面顶部的搜索框和正文编辑器都带 `editable`。按 `editable` 过滤会先抓到搜索框，第一次粘贴直接粘进去了，靠字数校验才拦住没提交。定位必须按 `role=textbox` + `editable=richtext` 双重过滤。

**坑 3：工具说 success，页面什么都没变。**
这是最贵的一类故障——agent 信了继续往下走，错误在第三步之后才暴露。所以"生效没有"必须是工具原语（前后快照 diff），不能靠事后自查。
