## 标题

`不 OCR 读 canvas：从绘制调用层拿文本的一次实践`

## 正文要点成稿（约 1500 字）

### 一、起因：DOM 方案在 canvas 面前是全瞎的

维护的一个自动化任务里有个环节：在白板类应用（Excalidraw）里确认"Agent 刚才写的字确实写上去了"。

这类应用整个画布是一个 `<canvas>` 元素，DOM 里除了这个标签什么都没有——基于 accessibility tree 或 DOM 快照的方案，拿到的是**空的**。截图路线能"看"，但一是每次交互一张图进上下文，视觉 token 成本是纯文本的几十倍；二是拿到图之后还要再过一道 OCR 去猜，猜错率随字体和背景波动。

但有个事实可以利用：**2D canvas 上的文字，是在 `ctx.fillText()` 里画出来的。** 绘制调用层就有原始字符串，根本不需要"看"。

### 二、方案：在绘制调用层截流

思路直接——给 2D context 的绘制方法挂 hook，把调用参数原样记下来：

- 时机：hook 只记录**安装之后**的新绘制，历史绘制不补（避免首帧全量噪音）；
- 字段：文本内容、字体、坐标、尺寸、颜色，全部来自 `fillText` 的实参，零猜测；
- 开关：默认关闭，显式开启后才记录（生产路径不为监控付出固定成本）；
- 边界：WebGL 不走这条路（绘制指令走 GPU，拿不到字符串），保留截图路径且默认关闭——这一条必须写清楚，不能拿 2D 的结论去套 WebGL。

实测一次完整读写：Agent 在画布上写了 45 个字符，读取返回：

```json
{
  "text": "AI Browser wrote this - no screenshot, no OCR",
  "font": "20px Excalifont, Xiaolai, sans-serif",
  "at": { "x": 10, "y": 13.2, "width": 937.4, "height": 42.2 }
}
```

字体、坐标、颜色全在，没有经过任何图像识别。

### 三、落地步骤

1. 开启画布捕获（显式开关，默认关）；
2. 确认只捕获安装后的新绘制（先 configure 再操作）；
3. Agent 执行绘制动作；
4. 从绘制层读回结构化数据，与预期字符串比对——**这就是一次可编程的验证**，比"截图看看写没写上"确定得多。

### 四、这个方法真正值钱的地方

表面看是"读 canvas"，实际是把**验证**变成了原语。

自动化的故障模式里，最贵的不是"点不到"，是"以为点了其实没点"——工具返回 success，页面没变，错误在三步之后才暴露。canvas 数据读取给了这类应用一个确定性的判据：DOM 零变动 ≠ 什么都没发生，绘制层的指纹变了就是变了。

配套的前后快照对比（显式 changed/unchanged + JSON path）也是同一个设计思路：把"操作生效了没有"从事后自查变成工具能力。

### 五、边界与风险（如实说）

- WebGL 应用不适用，仍走截图；
- hook 有微小性能开销，所以默认关闭、按需开启；
- 只读绘制参数，不干预渲染；
- 该能力在 macOS/Linux 环境验证，Windows 未测。

### 六、小结

canvas 不是自动化的盲区，只是换一层拿数据：2D 场景在绘制调用层，WebGL 场景才需要像素。顺带解决了一个更大的问题——验证的原语化。完整实现（Electron + CDP + MCP，MIT）在 GitHub：Glittering/ai-browser，跑不通欢迎贴日志。
