# v2.4.3

一次白屏 + 深红横幅的根治：**「视图对象还在」不等于「它还能碰」**。

## 现象与证据

用户报「刚刚又白屏了」，截图：标题栏正常（"在线白板工作台…迅捷白板"），
内容区几乎全白，左侧露一小块橙棕，底部一条**深红色横幅**。

翻 `~/.ai-browser/logs/error.jsonl` 找到同一个异常**反复 22 次**（10-26 起多次）：

```
TypeError: Cannot read properties of undefined (reading 'isDestroyed')
    at pushNavState (index.js)
    at WebContents.push → WebContents.emit
```

`pushNavState` 由 `setInterval(pushNavState, 1500)` 每 1.5 秒无条件驱动。

## 根因（用真 Electron 探针实测，不是推测）

`_probe_view_tmp.cjs` 三个决定性事实：

1. **`webContents.close()` / `destroy()` 之后，BrowserView 对象还在，但
   `view.webContents` 变成 `undefined`**。此时 `view.webContents.isDestroyed()`
   直接抛 TypeError —— 与日志一字不差。
2. **渲染进程崩溃（`render-process-gone`）后，`view.webContents` 还在、
   `isDestroyed()` 返回 false，但内容不再渲染**，视图区域空白，`reload()` 能救。
3. **`BrowserWindow.capturePage()` 对含 BrowserView 的窗口返回 `empty`** —— 它抓不到
   BrowserView 的合成结果。所以"用窗口层截图补白屏自检"这条路在 Electron 内置 API
   上走不通，只能走 Quartz/屏幕录制（要录屏权限、后台不可用）。因此**放弃像素通道**，
   改用更早、更可靠、零权限的信号（见下）。

完整因果链：

```
某个视图的 webContents 悬空（GPU 进程崩溃连带 / 系统回收渲染进程）
  → setInterval 每 1.5s 调 pushNavState
  → 裸访问 tabBarView.webContents.isDestroyed() → 抛异常
  → uncaughtException → reportFatal → showErrorBanner
  → layoutWithBanner 又碰悬空视图 → 处理器内部二次崩溃
  → 进程半死（端口 listen 但 WS 握不上手；日志里规律性的重启）
  → tabBarView 无 render-process-gone 监听、无重建 → 标签栏永久空白（白屏）
  → 横幅挂上后只能靠人点 × 收起 → 深红条挂了几小时，页面还被挤掉 34px
```

历史日志旁证：`child_process_gone` 里成片的 `GPU reason=killed`，正是这次
探针在无沙箱启动时复现的 `GPU process exited unexpectedly: exit_code=6` +
`Network service crashed` 循环。

## 修了什么（底层通用，不逐个打补丁）

### 1. 统一存活判定 `shared/view_liveness.cjs`（纯函数，可单测）

`isAlive(view)` 覆盖四种失效形态（`null` / `.webContents` 悬空 / `isDestroyed`
/ getter 抛异常），**任何情况都不抛异常**；`liveness(view)` 返回五态原因，让日志
能区分"悬空"（要重建）和"已销毁"。`index.js` / `page_manager.js` 里所有判定型的
裸 `.isDestroyed()` 访问全部收敛到它。node:electron 在 vitest 里 import 会炸，
所以这层判定必须抽成纯函数才能被单测钉死。

### 2. chrome 视图（标签栏）自愈

- `createTabBarView()` 工厂 + `ensureTabBarAlive(force)`：把原本每 1.5s 触发的
  **崩溃点**（`pushNavState`）改成 **自愈点** —— 每次推送前先体检，死了就重建。
- `tabBarView.webContents` 新增 `render-process-gone` 监听：渲染进程真的没了
  （killed/crashed/clean-exit）时主动报一声并触发重建，不必等 1.5s 轮询。
- 重建**有节流（≥1.5s 间隔）与上限（单进程 8 次）**：GPU 连续崩溃时不无限
  `new BrowserView`（那就是另一种死循环）。到顶写一条 `tabbar_rebuild_exhausted`。

### 3. 主进程兜底处理器自我加固

- `reportFatal` 整段包 try/catch —— 它跑在 `uncaughtException` 里，**自己绝不能
  再抛**（否则就是"处理器内部二次崩溃 → 进程半死"的元凶）。
- `uncaughtException` handler 对 `isDestroyed|webContents|destroyed` 类错误，除了
  记录，还主动做一次 `ensureTabBarAlive(true)` 纵深自愈。
- `showErrorBanner` / `layoutWithBanner` / `refreshTabBar` / `activeWebContents`
  全部走 `isAlive`，断掉二次崩溃的每一条路径。

### 4. 横幅自动收敛

以前横幅挂上只能靠人点 × 收起。现在静默 `BANNER_AUTO_HIDE_MS`（默认 15s，
可用 `AI_BROWSER_BANNER_AUTOHIDE_MS` 调）后自动收起，**日志里的 stack 永久保留**
（`ui.errors` 仍可查）。自动收起写一条 `error_banner_autohide`，让"横幅是不是
又挂死了"可观测。有新异常会重置计时器。

### 5. 白屏自检补上「视图已死」（治本，非像素补丁）

现有 `paintCheck` 用 `wc.capturePage()`（view 自己的 surface）。探针证实：
**渲染进程崩溃后它返回 `empty`**，而旧代码把"拿不到位图"一律判 `no-frame` →
`decidePaintAction('no-frame')` 返回 `none` → **静默放过，永久白屏**。

- `classifyPaint` 新增 `view_alive` 参数与 `view-dead` verdict：
  拿不到位图**且**视图已失效 → `view-dead`（要救）；视图还活着（被遮挡/隐藏）
  → `no-frame`（不动，避免后台重载风暴）。用"视图存活"这个更早、更可靠、
  零权限的信号替代了走不通的像素通道。
- `paintCheck` 开头遇到失效视图不再 `return {ok:false}`（那样 `_auditPaintNow`
  直接放弃），而是返回可判定的 `view-dead` 结论。
- `_auditPaintNow` 对 `view-dead`：webContents 仍可 reload 时重载一次；真正悬空或
  重载无效则**如实上报 `paint_blank`**（不盲目重建整个 tab —— 那会丢导航历史/
  分组/登录态，用户的页面不是重建试验场）。阶梯仅 `reload → give-up` 两级，
  有上限不循环。

### 6. 顺带清理

`_confirmAndFixLayout` 里 `return {fixed:'deferred'}` 之后有一段永远不可达的
"立即修正"旧代码（改成延迟确认时忘了删）—— 已删除。

## 实测（红 → 绿对照，隔离实例，隐藏模式）

`AI_BROWSER_SELFTEST=chrome-gone` 主动把 `tabBarView.webContents` 置为悬空：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `uncaught_exception` | 1（会滚成 22 次） | **0** |
| `error_banner`（深红横幅） | 1 | **0** |
| `tabbar_rebuilt`（自动重建） | 0 | **1** |
| 进程存活（WS 可握） | 半死 | **健康** |

`AI_BROWSER_SELFTEST=crash` + 短 autohide：横幅确实弹出（前提成立）→
`error_banner_autohide=1`（自动收起），收起后进程仍健康。

## 判据

- 单测 `tests/test_view_liveness.js` 11 条：四种失效形态、getter/isDestroyed
  抛异常不冒出去、isAlive 与 liveness 一致。
- 单测 `tests/test_blank_page.js` +3 条：`view-dead` 的阳性对照（必须报出来）、
  被遮挡仍 `no-frame`（不误报）、向后兼容、`view-dead` 阶梯有上限。
- e2e `npm run lifecycle` 9 条，已进 `e2e:all`：视图悬空不崩 / 真重建 /
  重建有上限 / 不误弹横幅 / 进程仍健康 / 横幅自动收敛。
  **关键**：这些断言在 jsdom 里写不出来 —— `webContents` 悬空是真 Electron 的
  行为，只有真浏览器能证伪「视图失效后主进程还活不活」。
- selftest 默认完全关闭，不影响任何生产路径。
- 全量：单测 **83 文件 / 1166 条**、e2e **25 套件 / 814 断言** 全绿（含新增 `lifecycle` 9，
  `focus` 也在全量串行里全绿）。

## 明确的边界

- 不引入 Quartz/屏幕录制做运行时白屏自检：Electron 内置 `capturePage` 抓不到
  BrowserView（探针实测），Quartz 要录屏权限且后台不可用。用"视图存活"信号替代。
- 页面 tab 的 webContents 悬空时**不盲目重建**（会丢用户状态），如实上报让人
  决定。chrome 视图（标签栏/横幅）是我们自己的、可安全重建的，才自动重建。
- `tabbar` 重建上限 8 次：GPU 反复崩溃到顶后停止重建并留日志，不无限循环。
- **`focus` 套件在多 app 抢前台时是 flaky，不是本次回归**：4 次对照证明——改动后单跑
  9270 红（前台=宿主 WorkBuddy）、改动前 stash 回退 9271 全绿、改动后 9272 全绿、全量串行红
  （前台=被测 Electron）。失败结果互相矛盾，且 `git diff` 证明本次改动零触及焦点路径
  （`_focusWebContents` / `tab_route` / show 逻辑都没动）。属测量环境问题（测量类测试先验前提），
  全量串行时前面套件刚操作过窗口/焦点，最容易触发。
