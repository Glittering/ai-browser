# v2.4.5 — 评估后一次性优化：能力静默失效 / 清理机制化 / 错误不许撒谎

这一版不是加功能，是**按评估报告整改**。完整报告见 `docs/AUDIT-2026-10-30.md`。

评估结论先说：架构方向是对的（三层分层清晰、61 个模块 58 个有单测、22 条不变量都有
回归），**没有 P0**。真正的风险在两处结构性隐患，它们不是"哪里写错了"，而是
"这类错必然还会再发生"：

1. per-tab 状态清理靠**手写列举** —— Bug 5 补过 4 个字段，这次又查出 3 个漏网；
2. MCP 层是**手写转发** —— 17 个工具、每个参数都要再抄一遍，抄漏了不报错、只是能力消失。

## P1-1 `browse_evaluate` 的 `frame_ref` 在 MCP 层被丢掉（能力静默失效）

schema 写着「Pass it explicitly when touching iframe content」，`ws_server` 也确实
把它传给 `pageManager.evaluate(js, tabId, { frameRef })` —— 但 MCP 的转发对象里
**没有这个键**。于是 agent 按文档传了，JS 仍在顶层帧执行、对 iframe 内元素返回
`null`。不报错、不告警，调用方只会得出"元素不存在"。

这是「同一概念在两层形状/名字不同 → 调用方不报错，只拿不到数据」的第 5 次
（前四次：`{tabId}` vs `filter.tab`、`js` vs `expr`、`uri` vs `uris`、
`page_probe` 默认导出漏键）。

- 修复：补转发。
- **判据**：新增 `tests/test_mcp_forwarding.js` —— 表驱动，把 schema 声明的每个参数
  与 `case` 块里真正出现的标识符做比对（归一化 snake/camel，扣除由 `mcp_args.js`
  接管的键，识别整包透传）。任何新参数忘了转发 = 红。
- 已知陷阱：第一版判据是**假绿**的 —— 它把注释里出现的参数名也算成"转发过"，
  删掉真正的转发后仍绿。已改为先剥注释再取标识符（阳性对照：删掉转发 → 2 条红）。

## P1-2 关 tab 的状态清理改成表驱动，补 3 个漏网

逐字段核对了 26 个 `this._x = new Map()/Set()`，漏清 3 项：

| 容器 | 键 | 后果 |
|---|---|---|
| `_openedTabs` | sourceTabId | 父 tab 关闭后永久留一条 URL |
| `_canvasBindings` | `__aiCanvasReport_<tab>_<rand>` | **每次重装 hook 生成新名字且永不删** |
| `_paintAuditInflight` | tabId | 异常路径不清 |

更有问题的是机制：新增任何 per-tab 容器，都靠人记得去 `_cleanupTabResources` 加一行。

- 修复：新增 `src/shared/tab_state.cjs`（`PER_TAB` 表 + `clearPerTab()` 纯函数，
  区分"键即 tabId / 值即 tabId / 定时器"三类），`_cleanupTabResources` 第一行调用它
  （纯删除不会抛，晚于它的 detach 万一抛了也不影响）。
- 顺手修 `canvasMonitor`：新增 `forget(tabId)`（连 `tabs` 条目一起删），
  `clear(tabId)` 保持"只清数据、保留 mode/hook"的语义
  —— `canvas_configure{clear:true}` 依赖后者，混用会让它"设了 mode 又丢掉 mode"。
- **判据**：`tests/test_tab_state_reset.js`
  - 行为：假 owner + 假定时器，验证三类容器各自怎么清、别的 tab 不受牵连、
    `clearTimeout` 真的被调到；
  - 闸门：静态解析 `page_manager.js` 里所有 `new Map()/Set()` 字段，必须登记在
    `PER_TAB` 或在 `NOT_PER_TAB` 白名单里（且写明理由）。新增容器忘登记 = 红。
  - 阳性对照：往构造函数里插一个 `this._ghost = new Map()` → 测试红并指名 `_ghost`。
- `tests/test_bug5_tab_close_cleanup.js` 同步改写：逐字段正则 → 接线断言
  （是否调了表、顺序是否在 detach 之前、函数体里是否又出现手写 delete）。

## P1-3 `ui.wait` 在导航期间整条失败

`poll()` 里 `await pageManager.getTree(...)` 没有 try/catch。而 `getTree` 在文档切换
窗口会 `reject('getTree timeout')`（硬 5s）—— `browse_wait` 最典型的用法恰恰是
「navigate 之后等条件出现」。

后果不是"等不到"，而是整条 RPC 变成 `-32603 internal error`；调用方看到"内部错误"
的合理反应是**重试导航**，把已经成功的导航再做一遍。

- 修复：单次抽取/求值失败视为"尚未满足"继续轮询；回执补 `attempts`（轮询次数）与
  `last_error`（仅在未满足时给，不静默）；`timeout_ms` 钳制到 `[100, 120000]`。
- 判据（`tests/test_ws_handlers.js` W-4/W-5/W-6，真 WS server + mock PageManager）：
  前两轮抛错 → 仍能等到 `satisfied:true`；一直读不到 → `satisfied:false` 且带
  `last_error`；传 1ms 也至少轮询一次。

## 明确不做（理由在报告里）

- 拆 `page_manager.js`（5859 行）：8 类职责共享同一批 tab 生命周期，现在拆会把
  "一处状态两处写"的风险放到最大。前置条件是本次的表驱动落地 + e2e 基线稳定。
- 统一 WS/MCP 的 camelCase vs snake_case：双轨各自自洽，真问题是"转发靠手抄"，
  已用闸门堵住；改名是破坏性变更。
- `ui.wait` 改用 `evaluate` 做轻量轮询：`button_enabled` 需要 id/label 匹配与 `states`，
  改等于把判定口径复制一份到 JS 字符串里（本项目吃过"两处实现各自演化"的亏）。
