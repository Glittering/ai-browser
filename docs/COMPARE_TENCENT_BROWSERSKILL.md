# 与腾讯浏览器 Agent 的方案对照

> 2026-10-19 · 对照对象：`Tencent/BrowserSkill`（开源，MIT，~9k star）与 `QBotClaw`「龙虾」（QQ 浏览器内置的消费级产品）
>
> 本文回答三个问题：**我们和别人差在哪、我们领先在哪、哪些东西值得抄、抄的时候怎么抄才不变成打补丁。**

---

## 0. 先说清楚比的是谁

腾讯手上有**两个完全不同**的东西，很容易混为一谈：

| | BrowserSkill | QBotClaw「龙虾」 |
|---|---|---|
| 形态 | `bsk` CLI + 本地 daemon + Chrome/Edge 扩展 | QQ 浏览器内置侧边栏 |
| 面向 | **agent**（Claude Code / Cursor / Codex / OpenClaw…） | **普通人**（一句话干活） |
| 哲学 | 借你已登录的浏览器，用完归还 | 浏览器本身就是 Agent |
| 对我们的参考价值 | **架构与工程纪律**（主要） | 产品形态与冷启动（次要） |

下面 80% 讨论 BrowserSkill，因为它是唯一一个和我们在同一层（agent 的浏览器能力层）竞争的东西。QBotClaw 只在第 7 节作为产品参照出现。

---

## 1. 一句话结论

**我们和 BrowserSkill 是同一道题的两种解法：他们选择「不换浏览器」，我们选择「换一个浏览器」。**

- 他们赌：用户的登录态、插件、习惯都在现有 Chrome 里 → 扩展 + 守护进程把它借出来，成本最低。
- 我们赌：只有自己造浏览器，才能拿到**语义树、canvas 绘制层、网络层**这些 DOM 之外的信息通道 → 上限最高。

两个赌注都不错，但**我们目前的产品工作重心偏了**：过去几轮一直在补"能不能点开这个页面"这类站点兼容性，而 BrowserSkill 把精力花在了**"agent 怎么知道自己的动作到底生效了没有"**这种更底层的问题上。这才是这个产品真正的护城河所在——因为站点是无穷的，而正确性模型只有一个。

---

## 2. 定位：三种赌注

```
            上限高（能读懂一切 / 能操作一切）
                    ▲
                    │
        ai-browser  │            （无人占据：
     自带内核+语义树 │              既要上限又要零迁移成本）
                    │
                    │        BrowserSkill
                    │     借现有浏览器+扩展
                    │
                    │  QBotClaw
                    │ 内置一句话自动化
                    └──────────────────────────► 迁移成本低（用户不用改习惯）
```

关键判断：**我们的定位（AI 独驾 + 真实可见 + 无常驻交接协议）是对的，而且比 BrowserSkill 的 borrow/return 模型更简单。** 他们必须设计"借用表、权限闸、归还路由"，是因为他们要在用户自己的工作环境里动手，得防着踩到用户的 tab；我们的窗口从头到尾就是 agent 的，人只是坐在旁边随时能伸手——这套复杂性在我们这里**根本不存在，也不应该被引入**。

但"简单"是有代价的：**用户必须换浏览器**。这个代价只能靠"换过去之后明显更强"来偿还。所以第 5 节那几件事，本质是在回答"我们凭什么值得用户换"。

## 3. 架构对照

| 维度 | ai-browser | BrowserSkill |
|---|---|---|
| 内核 | 自带 Electron 33 / Chromium 130+，每 tab 一个 BrowserView | 复用用户的 Chrome/Edge（扩展要求 Chromium 125+） |
| 进程 | main + renderer + preload + 各 tab CDP | CLI(Rust) + daemon + MV3 扩展(service worker) + 页面 CDP |
| 内部传输 | 进程内 IPC（`ai:*`） | CLI ↔ daemon：UDS 上的 JSON Lines；daemon ↔ 扩展：loopback WebSocket（默认 52800） |
| Agent 接入 | MCP stdio（20 个 `browse_*`）+ WS JSON-RPC（`ui.*`） | **`bsk` 命令行**（21 个 tool handler）+ 可选 MCP/DSH 插件 |
| 会话模型 | 单浏览器实例，多 tab，`activeTab` 隐式 | session = 随机 ID + 独立 Agent Window + 会话级元素 refstore + 借用表 |
| 元素寻址 | `data-ai-id`（注入的稳定 ID） | `@e1`（**会话作用域**的 ref，随会话销毁） |
| 并发 | 未做队列（同 tab 靠调用方自律） | **每 session 串行队列**，不同 session 并行 |
| 窗口 | 一个主窗口，tab 条自带 | 用户窗口 + 多个隔离 Agent Window（每 session 一个） |
| 部署 | 纯本地 | 本地 / **远程**（浏览器在用户机、daemon 在服务器、出站 WSS、设备配对+吊销） |
| 规模 | `page_manager.js` 3809 行 | CLI/daemon(协议层) / 扩展(工具分发/会话管理/驱动) 分层清晰 |
| 技能包 | `examples/AGENT_INSTRUCTIONS.md` | `SKILL.md` + `references/`，带 SHA-256 清单、原子更新、20s 回滚 |

**最扎眼的一条**：他们把"agent 怎么用我"做成了**版本化的、带校验和可回滚的交付物**（skill 包），而我们只是一份 README。

## 4. 页面理解与数据形态

这是我们的主战场，也是差距和优势同时最大的地方。

| 能力 | ai-browser | BrowserSkill |
|---|---|---|
| 语义树 | ✅ 读层主力（AX + 自研 extractor，1400 行） | 部分（"inspect page text and controls"） |
| Canvas 内容 | ✅ **绘制调用层截获 `fillText`**（独特） | ❌ 只有 DOM facts + 截图 |
| 网络抓包 | ✅ 含 POST body、敏感头脱敏 | 部分（调试证据：响应体、console） |
| 操作生效性验证 | ✅ `browse_diff` 显式 changed/unchanged | 部分（`observe`，无 diff 原语） |
| 结构化数据提取 | ❌ **完全没有** | ✅ 表格/列表 → JSON/CSV，带列名、frame 来源、合并单元格、**覆盖率** |
| 每步追溯 | ❌ 只有错误码 | ✅ 每个工具返回 `steps`（做了什么/成功还是跳过/耗时），失败**自动附现场截图** |
| 副作用语义 | 半成品（超时错误里写了"可能已部分生效"） | ✅ **`effect_state`: none / committed / unknown**，且规定 unknown 不许盲目重试 |
| 登录态 | 常驻 `persist:` 分区 + 退出固化会话 cookie | 直接用用户 profile，天然共享（但明说"不是沙箱"） |
| 只读证据留存 | 无 | 调试证据 30 天 / 50 条 / 50MiB；审计默认关且只记元数据；视频可选加入 |

注意表格里有两行鲜明的对照：**「结构化数据提取」和「每步追溯」我们是空的，「canvas / 网络 / diff」是空的。**

## 5. 值得抄的六件事（按价值排序）

### ★★★ 5.1 把「动作效果」变成结构化字段：`effect_state`

**他们怎么做**：每个会产生副作用的操作都报三态——`none`（确定没生效）/ `committed`（确定生效）/ `unknown`（不确定），外加 `phase`、`cleanup_state`。硬规则是：**`unknown` 不得盲目重试**，超时或传输中断后必须保留这个判断。

**我们现状**：`browse_act` 返回 `{success, clicked_via, target, opened_tab}`，超时分支的 error 文本里已经写了"the action may have partially applied"——**这个洞察我们有，但只活在一条人类可读的字符串里，agent 没法据此做判断。** agent 只能猜：该重试，还是该先看一眼页面。

**为什么这是第一优先级**：它是**架构级、通用、不可绕过的**。语义树再准、工具再多，只要 agent 无法区分"点了但没反应"和"点了不知道有没有反应"，它就会重复点击、重复提交、重复支付。这是所有站点兼容补丁的总根，不是某一个站的问题。

**怎么落地**（`page_manager.js`，不新增工具）：
- `_executeActionInner` 的每个分支统一产出 `effect: 'none' | 'committed' | 'unknown'`
- 判定规则要具体：CDP 输入命令 resolve 且元素仍在 → committed；deadline 命中 / debugger 分离 / 导航中断 → unknown；ref 解析失败、元素 detached → none
- 已有 `browse_diff` 事后验证仍然保留，两者互补：`effect` 回答"我这个动作"，`diff` 回答"页面变了没有"
- 文档里写死一句话：**`unknown` 时先 `browse_get_tree`/`browse_diff` 复核，不要重试**

### ★★★ 5.2 结构化提取：表格/列表 → JSON/CSV

**他们怎么做**：扩展侧只采集**有界的 DOM 事实**并归一化表格/列表，CSV 编码放在 CLI 侧；输出带列名、page/frame 来源、合并单元格元数据，并**明确声明覆盖率**（哪些行/列没取到）。

**我们现状**：完全空白。agent 拿到语义树后要自己拼表格，token 贵、结果不稳定。

**为什么该做**：这是 agent 落地场景里**最高频的产出物**（"把这个月的订单导出来""对比这两个商品的价格"）。而且它天然符合我们的定位——**给 agent 结构化数据，而不是截图**。比起继续加站点兼容补丁，这一个通用能力能吃掉一整类需求。

**怎么落地**：挂在现有 `browse_get_tree` 的 `context` 里（保持工具数不变），加 `format: 'table'` 子模式；输出 `{columns, rows, frame, coverage: {rows_seen, rows_total, truncated}}`。**覆盖率必须报**——这是他们做得比大多数方案都诚实的一点。

### ★★ 5.3 每步追溯（steps）+ 失败自动留证

**他们怎么做**：每个工具返回值里带 `steps`：做了什么、成功还是跳过、耗时多少；失败时自动附失败现场截图，"让 LLM 能接着手工收尾"。

**我们现状**：失败只有一个 error 字符串。用户问"它到底卡在哪一步"时，我只能去翻窗口。

**为什么该做**：这是**给 agent 的调试接口**，不是给人看的日志。有了它，agent 才有可能自己从失败里恢复，而不是把整个任务甩回给人。

**怎么落地**：主进程侧一个轻量 `trace` 收集器（不是日志系统），随返回值附回；截图复用已有 `browse_screenshot` 的底层调用，只在失败路径触发。

### ★★ 5.4 元素引用的作用域与生命周期

**他们怎么做**：`@e1` 是**会话作用域**的 ref，存在 refstore 里，会话结束即失效；`click @e1` 必须带 session。

**我们现状**：`data-ai-id` 注入进 DOM，跨导航漂移、旧 ID 可能指向新元素。这是静默错点的温床。

**为什么该做**：**不是学它的 borrow 模型，而是学它的"引用有寿命"这个纪律。** 一个 ID 在页面重渲染后还"能用"，是比"不能用"更危险的事。

**怎么落地**：`get_tree` 返回时给每个 ID 打上 `tree_epoch`；`act` 校验 epoch，过期就明确回 `stale_ref: true` 并附最新树的可选项。零新增工具。

### ★ 5.5 把「教 agent 怎么用」当交付物

**他们怎么做**：`SKILL.md` + `references/`，构建时嵌入二进制，带逐文件 SHA-256 清单、新路径冲突检查、原子替换、失败 20s 回滚旧版。

**我们现状**：一份 `examples/AGENT_INSTRUCTIONS.md`，和代码版本不联动。

**为什么该做**：工具的正确用法（比如"点击后必须 diff 验证"）如果能随版本分发，能消掉大量"agent 用错"的假 bug。我们这次修的 about:blank，本质就是**站点用了我们没预料到的 API 语义**——同理，agent 也会用我们没预料到的工具组合。

### ★ 5.6 安全边界要「可声明」

**他们怎么做**：审计默认关闭且只记元数据（排除输入值、页面正文、截图）；调试证据 30 天过期；脱敏后**明确说"不能保证全部去除"**；视频帧**不自动脱敏**，提醒用户自己看。

**我们现状**：没有一句话回答"我把银行页面交给它，会发生什么"。

**为什么该做**：开源项目最大的阻力不是功能，是**敢不敢用**。一套诚实的边界声明比一堆安全特性更有说服力。

## 6. 我们已经领先、必须守住的东西

这四条不要因为"别人没有"就以为不重要：

1. **Canvas 绘制层读取**。BrowserSkill 只有 DOM facts + 截图。纯 canvas 应用（excalidraw / ComfyUI / 各类编辑器）在他们那里是瞎的，在我们这里是可读的。**这是唯一一个他们抄不走的点**——要抄得换内核。
2. **网络层**。含 POST body 的抓包，能回答"这个表单到底提交了什么"。这是 agent 自查的硬证据。
3. **`browse_diff`**。显式 changed/unchanged。他们只有 observe，没有"证明"这个概念。**这一条加上 5.1 的 effect_state，就是完整的正确性闭环**：动作声明效果 → 页面证明变化。
4. **工具面的 token 经济**。他们每次调用要带 `--session ab12 --tab-id 42`；我们的 tab 是隐式 active。**对 agent 来说这是每步都省一笔上下文开销**，长期跑长任务的差距会累积。这一点别改。

顺带一个反直觉的观察：他们的 21 个 tool 和我们的 20 个数量相当，但**他们的工具是"动词-名词"命令式（`bsk click @e1`），我们的是"读—动—验"三元组（get_tree / act / diff）**。后者的形状更贴近 agent 的实际循环：看 → 动 → 确认。这是设计上的优势，不是巧合。

## 7. 我们「偏」在哪（诚实清单）

| # | 偏移 | 证据 | 判断 |
|---|---|---|---|
| 1 | **工具数从锁死的 13 涨到 20** | `PLAN_PRODUCT.md` 明写"锁死 13，一个都不加" | 已经有 7 个新增。`auth_state`/`errors` 治的是真痛点（该加），`repaint` 是给渲染 bug 打的补丁（该在内部修掉，而不是变成 agent 的负担），`capabilities` 是"让 agent 自己猜该走哪条路"——这本质是把我们的不确定性转嫁给 agent |
| 2 | **`page_manager.js` 3809 行** | `PLAN_ARCHITECTURE.md §3` 早就规划了拆分步骤 Step 0–9 | 没执行。所有新能力都往一个文件里塞，这是"打补丁"的物理形态 |
| 3 | **重站点兼容，轻正确性模型** | 最近几轮全在修某个站打不开/点不动 | 站点无穷，正确性模型只有一个。BrowserSkill 在后者上比我们走得远 |
| 4 | **没有"这一步做了什么"的可观测** | act 失败只有一个 error 字符串 | 出问题时只能靠人肉看窗口，agent 无法自愈 |
| 5 | **没有结构化产出** | 无表格/列表导出 | agent 最高频的产出物反而是空白 |

第 1 条要点名：**"capabilities 让 agent 自己选路"这个设计方向，和 BrowserSkill 的"工具只做确定的事"是相反的。** 前者把复杂度推给模型，后者把复杂度留在实现里。我们的定位是"底层、通用、好用"，应该选后者。

QBotClaw 值得看的只有两点，且都不是现在该做的：**微信远控**（人在外面也能指挥家里的电脑）和**扫码即用**（零配置冷启动）。这是分发层面的启发，不是架构层面的。

## 8. 落地路线

按"改完就不需要再改"排序，不按工作量排。

**P0 — 正确性闭环（1 个 PR，不新增工具）**
1. `effect_state` 三态 + `unknown` 不重试纪律（§5.1）
2. 元素引用加 `tree_epoch`，过期明确报 `stale_ref`（§5.4）
3. 失败路径自动留证（复用 screenshot 底层）（§5.3 的一半）
4. 补测试：`tests/test_effect_state.js` 覆盖 committed / none / unknown 三态，特别是**超时后必须是 unknown 而不是 none**

**P1 — 结构化产出（1 个 PR）**
5. `get_tree` 增 `format: 'table'`，输出 columns/rows/frame/**coverage**（§5.2）
6. 用两个真实站点（一个电商列表、一个后台表格）做 e2e，把"取不全时如实报覆盖率"写成断言

**P2 — 收口与减法**
7. 按 `PLAN_ARCHITECTURE.md §3` 真拆 `page_manager.js`（先拆 network / canvas / ax 三块，它们已经是独立文件了，把调用点也搬过去）
8. 重新审视 `capabilities`：如果 agent 用它选路的结果不比"直接试 act + diff"好，就删掉
9. skill 包化：`AGENT_INSTRUCTIONS.md` → `skills/ai-browser/SKILL.md` + `references/`，随 npm 包版本分发（§5.5）

**不做**
- 不做 borrow/return / Agent Window 沙箱：我们从来不借别人的浏览器，这套模型是**为他们的赌注付的税**，我们没有这个赌注
- 不做远程 daemon：现阶段目标用户是"一个开发者 + 一个 agent + 一台 Mac"，加了就是纯负担
- 不把工具数当 KPI：宁可 17 个各司其职，不要 21 个互相重叠

## 9. 一页速查

| | 该学 | 该守 | 该砍 |
|---|---|---|---|
| 概念 | effect_state 三态、引用有寿命、覆盖率诚实 | canvas / 网络 / diff 三件套 | capabilities 让 agent 自己选路 |
| 形态 | 结构化提取、steps 追溯、skill 包 | 隐式 activeTab 省 token | 工具数继续膨胀 |
| 工程 | 分层、原子更新回滚、边界可声明 | 自带内核带来的确定性 | page_manager 单文件巨石 |

**最后一句判断**：我们和 BrowserSkill 差的不是功能数量，是**"工程上有多相信自己说的话"**。他们连"unknown 不许重试""脱敏不能保证全部去除""保留的任务记录不等于删除"都写进了文档；我们连"这个点击到底生效了没有"都还只能靠 agent 猜。补上这一层，比再修十个站点更有价值。
