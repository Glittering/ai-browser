# 代码与缺陷评估 — 2026-10-30（v2.4.4 基线）

> 范围：`src/` 全部 61 个模块（20.5k 行）、`tests/` 88 个文件 1191 条、`e2e/` 38 个文件
> （`e2e:all` 25 套件）。方法：静态链路核对 + 单测实测 + 受控 mock 行为验证。
> **只列有证据的条目**；无法证实的标「待确认」，不写成缺陷。

## 一、总体判断

架构方向是对的，且比同类项目更克制：

| 维度 | 结论 |
|---|---|
| 分层 | `ws_server`（40 个 RPC）→ `page_manager`（唯一状态持有人）→ `preload`/`shared`（纯函数）三层清晰，参数映射集中在 `mcp_args.js` 单点 |
| 可测性 | 61 个模块里 **58 个有单测**；纯函数大量下沉到 `shared/`（35 个模块合计 4.0k 行），这是"判据可测"的前提 |
| 不变量 | 22 条已固化的教训都有对应回归，且**写明了证伪方式**（这是本项目最值钱的资产） |
| 观测 | 错误日志 / `paint_check` / `canvas` 帧指纹 / `effect_state` 三态，失败形态可查 |

**主要风险不在"哪里写错了"，而在两处结构性隐患**：

1. **`page_manager` 有 26 个 per-tab 容器，清理靠手写列举**。Bug 5 只补了当时被点名的 4 个，实测还有 3 个漏网（见 P1-2）。这类缺陷会随"新增一个 per-tab Map"无限复发 —— 属于必须用结构消灭的一类。
2. **MCP 层是"手写转发"**：17 个工具、每个参数都要在 `mcp_server.js` 里再抄一遍。抄漏了不报错，只是能力静默失效（P1-1 就是第 5 次同类事故）。

## 三、P1

### P1-1 `browse_evaluate` 的 `frame_ref` 在 MCP 层被丢弃（能力静默失效）

- 位置：`src/main/mcp_tools.js:135`（声明）→ `src/main/mcp_server.js:151`（只转发 `js`/`tab`）
- 事实：schema 明确写「Pass it explicitly when touching iframe content」，`ws_server.js:453` 也确实把
  `params.frame_ref` 传给 `pageManager.evaluate(js, tabId, { frameRef })`；但 MCP 路径的转发对象里
  **没有这个键**，所以 `params.frame_ref` 恒 `undefined`。
- 影响：agent 按文档传 `frame_ref` 时，JS 仍在顶层帧执行、对 iframe 内元素返回 `null`。
  **不报错、不告警** —— 调用方只会得出"元素不存在"的错误结论。这正是「同一概念两层名字/形状不同」
  的第 5 次复发（前 4 次：`{tabId}` vs `filter.tab`、`js` vs `expr`、`uri` vs `uris`、
  `page_probe` 默认导出漏键）。
- 验证：`tests/test_evaluate_frame_ref.js` 只覆盖 WS 层，MCP 层零覆盖 → 这就是它能活下来的原因。
- 修复：补转发 + 新增 `tests/test_mcp_forwarding.js`（表驱动：schema 声明的每个参数，必须在
  对应 `case` 块里出现，或由 `mcp_args.js` 的映射层接管）。

### P1-2 per-tab 状态清理漏 3 项，且机制仍是"手工列举"

- 位置：`src/main/page_manager.js:4760 _cleanupTabResources`
- 事实（逐字段核对了 26 个 `this._x = new Map()/Set()`）：
  | 容器 | 键 | 关闭 tab 时 |
  |---|---|---|
  | `_openedTabs` | `sourceTabId` | **不清**（`page_manager.js:3856` 写入，仅被消费时删） |
  | `_canvasBindings` | `bindingName`（含随机后缀） | **不清**（`5206` 每次装 hook 生成新名，永不删） |
  | `_paintAuditInflight` | `tabId` | 正常路径自清，**异常路径不清** |
  | 其余 20 个 | — | 已清（含 Bug 5 补的 4 个） |
- 影响：`_canvasBindings` 每次重装 hook 新增一条且永不释放（长会话 × 反复 configure 会累积）；
  `_openedTabs` 在父 tab 关闭后永久保留一条 URL。两者都不大，但**机制问题才是重点**：
  现在新增任何 per-tab 容器，都靠人记得去 `_cleanupTabResources` 加一行。
- 修复：把清理改为**表驱动**（`src/shared/tab_state.cjs` 的 `PER_TAB` 表 + `clearPerTab()`：
  值匹配型/键匹配型/带 `clear()` 的对象三类），并加"完整性闸门"单测 ——
  构造函数里的每个 `new Map()/Set()` 必须登记在表里或在 `NOT_PER_TAB` 白名单里（写明理由），
  否则测试红。这样"忘清理"从一类 bug 变成一次构建失败。

### P1-3 `ui.wait` 在页面导航期间整条失败，而不是继续等

- 位置：`src/main/ws_server.js:730-757`
- 事实：`poll()` 里 `await pageManager.getTree(false, tabId)` 无 try/catch。`getTree` 在
  文档切换中会 `reject(new Error('getTree timeout'))`（`page_manager.js:1150-1155`，硬 5s）。
  抛错 → `poll()` reject → 整个 RPC 变成 `-32603`。
- 影响：`browse_wait` 最典型的用法就是「navigate 之后等某条件出现」，而这段时间恰恰是
  tree 抽取最不可靠的窗口。调用方拿到的是内部错误，不是 `satisfied:false`，
  于是会**重试导航**（把已经成功的导航重做一遍）。
- 修复：单次抽取失败视为"尚未满足"继续轮询，把最后一次错误放进回执 `last_error`（不静默）；
  `timeout_ms` 钳制到 `[100, 120000]`；回执补 `attempts`。

## 五、核对通过（避免下次重查）

1. **17 个 MCP 工具的其余参数全部有对应转发**（逐工具比对：navigate / get_tree / act / scroll /
   wait / auth_state / screenshot / tabs / network / canvas / diff / capabilities / repaint /
   downloads / errors / quit）。唯一的漏项就是 P1-1。
2. **文档里的工具名没有幽灵工具**：`llms-install.md` 出现的 `browse_subscribe` /
   `browse_network_body` 是**否定句**（"There is no …"），不是承诺。
3. **`browse_act` 的 13 个动词全部有执行器**：`get_value/click/hover/type/setContent/clear/paste/
   upload/drag/wheel/press` 在 `executeAction` 分支里，`focus/scroll_to` 在
   `preload/actions.cjs` 的 switch 里。无"广告了但没有 case"。
4. **`networkList` 的参数形状一致**：`ws_server` 传 `{tab, ...}` → `NetworkMonitor.list` 读
   `filter.tab`，无历史坑复发。
5. **`downloads` 的签名差异是安全的**：`downloads(params)` 读 `params.tab`，与 `ws_server:859`
   的 `{tab: tabId}` 一致（其余方法是 `(tabId, opts)`，两套风格并存但不冲突）。
6. **会话清理完整**：`unregisterClient` 清 `_wsClients`/`subscriptions`/`_sessionTab`。
7. **BUG6/BUG7 判据已行为化**（真进程双开、`listenerCount` 计数），不是源码 grep。

## 六、本次明确不做（附理由）

- **拆 `page_manager.js`（5859 行）**：它确实是最大单体，但 8 类职责共享同一批 tab 生命周期，
  现在拆会把"一处状态两处写"的风险放到最大。真要动，前置条件是 P1-2 的表驱动落地 + 全量 e2e
  基线稳定 —— 建议独立一轮做，不在"顺手优化"里夹带。
- **统一 WS 与 MCP 的参数命名（camelCase vs snake_case）**：WS 是内部协议、MCP 是对外协议，
  现有双轨各自自洽。真问题是"转发靠手抄"，P1-1 已用闸门堵住；改名是破坏性变更，收益不抵风险。
- **`ui.wait` 用 `evaluate` 替代 `getTree` 做轻量轮询**：`button_enabled` 需要 id/label 匹配与
  `states`，改成 evaluate 等于把判定口径复制一份到 JS 字符串里（本项目已经吃过"两处实现各自演化"
  的亏）。本轮只修"错误处理"，不动判定来源。
